# Stage handoff invariant

A stage starts only on explicit user activation or an assignment from an explicitly invoked Director whose task covers that stage. A readiness token or proposed next action is not activation authority. Apply the shared [authority contract](authority-contract.md); preserve each source, delegated permission and owner/model constraint in the handoff. Corrections to an existing upstream owner return through the parent, not a competing writer.

Read [technical decisions](technical-decisions.md) once for decision/journal semantics. Consume applicable current entries before implementation or judgment. If `context.technical_journal.requires_current_journal_read` is true, retrieve the canonical current map and relevant full records first; a locator or clipped preview is not delivered evidence.

When a Director supplies `control_binding`, apply the small shared [control-return contract](control-return.md) outside existing semantic artifacts/native stage handoffs. Native assignments and caller tasks have different bindings; never fabricate runtime IDs for upstream readiness, idle answers or recovery evidence. Standalone calls keep their existing public result. A bounded caller task requests only its stated existing-role work, not an automatic stage restart. Ignore ordinary commentary; only bound control requests/results or host completion need routing.

## One owner and one current assignment

Requirements, Specification and Planning use their own artifacts and controller lifecycle; runtime `active_assignment`/`complete` do not apply to them. For production phases, the controller issues the assignment identity, stable `worker_id`, read/write scope, checks, `artifact_schema` and exact workflow-local `output_path`. Do not invent or edit them. Assignment identity and physical agent identity are distinct: reuse the same eligible owner for successive assignments with its same alias, especially Engineering remediation. Review and QA remain independent from the implementation owner and each other; reusing their own role context grants no stale evidence.

The issued assignment authorizes its owner to write the exact terminal `output_path` under its artifact schema, including read-only Review and QA. This output right is separate from product `access.write` and any controller-command grant; an empty product write scope does not require a new capability request for that output. It permits no other control, state, history or Delivery writes, product scope expansion or native command. Other workflow-local requests require their own existing sanctioned route. An actual filesystem/tool denial still follows the capability route.

Before project file work, bind the explicit absolute controller `project_root` from delivery/handoff. Resolve every relative product read, write, delivery and artifact output path under that root, and set shell/tool cwd to it explicitly; inherited process cwd, a historical `file://` entry or a document example never selects another checkout. Exact absolute runtime/SKILL locators remain their supplied sources. Root binding grants no extra access: retain assigned read/write scope and exact output path. If root is missing or conflicts, return the bounded clarification before file work. Missing product files in an assigned greenfield implementation scope are files to create there, not evidence that a different project root should be chosen; a missing mandatory input still follows its actual prerequisite rule.

A new physical worker starts with no inherited conversation and receives a self-contained current packet. The same owner may consume a verified delta only while it retains the full applicable baseline. A worker has at most one active write lease; it finishes all owned mutating activity before returning its terminal artifact. Other actors do not mutate its checkout concurrently. Planned commands remain controller-owned, including diagnostic checks requested while Engineering or read-only QA is active. See the [delivery contract](delivery-contract.md) for complete reads and same-owner updates.

An informative control event is not a host-turn stop boundary. Under an active bounded native-check grant, Engineering or QA continues check, complete fresh delivery consumption and authorized work in the same host turn; no acknowledgment or renewed unchanged grant is required. A required control pause still applies at relay/missing access, semantic/authority or technical-request boundaries, actual control errors and context loss; terminal output stops owned work. Host-turn completion alone never completes the native assignment or grants phase PASS. See [active checks](execution-contract.md#check-inside-active-engineering-or-qa) for grant lifetime and quiescence.

## Working-set checkpoint and rotation

Do not wait for a fixed percentage of an enormous context window or rotate simply because a stage has a new assignment ID. Assess the useful working set: current authority and code, open findings, decisions, pending evidence, repeated rereads and remaining task. Checkpoint after a coherent implementation boundary or before foreseeable context loss. Reuse when the owner retains this set cheaply; rotate when lost/truncated material, repeated reconstruction or unrelated accumulated history makes a clean handoff cheaper or safer. Token/context telemetry is evidence, not a universal percentage trigger.

A checkpoint contains current project root, phase and generation, active assignment/owner, completed changes and uncompleted behavior, exact evidence/results, open finding IDs, relevant current decisions, pending child/result, authorized remaining files and exact next public action. Link source artifacts instead of copying history, transcripts, superseded decisions or private reasoning. Never mark incomplete work PASS to reach a boundary. Before replacement, establish quiescence and consume the actual result through the controller; use its idle `rotate-owner` route when a new role alias is needed. Replacement reads current authority and a full packet before work. A task or assignment is complete only when its own contract is satisfied; that boundary does not end the Director's full-cycle request.

## Evidence, artifacts and incidents

Read [interaction and evidence](interaction-evidence.md) before environment actions. Skills are platform-neutral; use explicit user-approved product authority or observed project or runtime capability. Passing a fixture does not prove a production integration; unexecuted mandatory checks remain unverified. A reproduced repairable defect is fail, not a user/environment blocker.

The issued artifact schema is authoritative. The worker follows its required/allowed keys and item shapes; native `complete` validates it. The Director checks exact output identity and actual lifecycle, not a duplicate JSON/schema validator. Omit empty optional fields. `blocked` requires non-empty `blocker` and `required_action`; `questions` is only for reversible technical clarification on pass. On bound artifact rejection the same worker corrects its representation truthfully where sufficient; if substantive work/evidence is missing it follows its actual role outcome, never fabricates checks/PASS. Do not replace the role for formatting. Slicer caller records contain only `id`, `allowed_paths`, `planned_commands`; sealed read access is controller-owned.

Use public error categories and factual evidence to distinguish stale action, malformed artifact, product failure, missing capability, authority/scope conflict and runtime incident. A suspected invariant/runtime defect pauses affected product transitions: workers MUST NOT edit, patch, bypass or locally replace the pipeline under product-only authority. Follow [maintenance observation](maintenance-observation.md) under applicable separate authority, including a valid prior delegation; otherwise report a real blocker. No speculative incident classification authorizes repeated retries or framework edits.

Workers stop after terminal artifacts. Directors follow [Director lifecycle](director-runtime.md): own each live child and consume every terminal result. A status question is steering, not completion or permission to abandon an unconsumed result.
