# Stage handoff invariant

A GameDev stage starts only when the user explicitly invokes it or an explicitly invoked `$gamedev-pipeline` Director assigns that exact phase. A completion token, repository state, or suggested next action is never activation authority.

Read the shared [technical decisions](technical-decisions.md) policy. Every role consumes current relevant journal decisions within its own authority; an unexpected result requires investigation before terminal classification. The journal records every encountered blocker, including successful autonomous resolutions, without granting a waiver or a new role.

If `context.technical_journal.requires_current_journal_read` is `true`, retrieve the canonical current map and select relevant entries before implementation or judgment, as required by that policy. Carry this mandatory read through fresh, replacement, and repeated-stage handoffs; the bounded projection or its pointer alone does not satisfy it.

Requirements, Specification, and Development Plan use their own role ownership, artifacts, and controller commands. They do not have runtime `active_assignment` or `complete`; their contracts govern child-result consumption. The assignment and artifact rules below apply to the seven production phases issued by the runtime. Each such assignment runs in a fresh worker context. The worker receives exact `feature` and `workflow_path`, a bounded task, relevant approved sources, read/write limits, checks, and the controller-derived `active_assignment.artifact_schema` and `active_assignment.output_path`. It follows that schema instead of reading runtime code or guessing, and writes its terminal JSON artifact only to that exact `.agentic-pipeline/Workflows/<feature>/outputs/<safe-assignment-id>.json` path; this controller-owned output area is outside candidate checkout evidence. It does not receive other controller bookkeeping, previous worker conversation, or authority to start another phase. The active Engineering technical-action request is a separate bounded workflow-local JSON permitted by the linked technical-decisions policy; it does not complete the assignment. The worker is the sole product mutation owner during the assignment, stops before returning its artifact, never runs controller-owned planned commands, and finishes its owned mutating activity before returning the artifact.

Preserve any stage owner and model constraints assigned by the user or parent, and include them in the relevant handoff. Read and apply the [agent model policy](agent-model-policy.md) for explicit role defaults, actual dispatch arguments, and continuity of existing owners. If upstream correction belongs to an already assigned stage owner, return the exact conflict and required correction to that owner through the parent before any upstream revision or replacement delegation. When no separate upstream owner is assigned and the invoked Director has authority to delegate that stage, use its existing upstream workflow autonomously.

## Context checkpoint and rotation

Context-use percentages describe the current agent session, not the plan's capsule/file/token budgets. A worker stops when its task or assignment is complete; a phase boundary returns control to the Director. It does not end the Director's run. Director completion follows the child-result consumption rule below; a real blocker or an explicit user stop still ends ordinary work. Those are lifecycle outcomes, not context-only rotation.

An active agent MUST NOT rotate or hand off solely because of context below 70%; it continues useful in-scope work. At 70% context use, record or refresh a compact checkpoint and continue. At 90% context use, hand off and stop: start no new work and perform only the minimum needed to leave durable, internally consistent state before 100%.

The checkpoint and final handoff contain only the current project root, phase and generation, active assignment, completed changes, test results, open blockers, current journal locator and relevant decisions, exact next public action, files still authorized for change, and any unavailable environment already tried with its capability evidence. Do not transfer prior conversation, superseded decision versions, or raw reasoning. A replacement validates current controller state, journal applicability, and authority artifacts before continuing.

Count a required read as complete only when its relevant content was actually delivered to the current agent. Bound the total output of a batched tool call as well as each nested read, and explicitly return the needed results. Reuse complete, unchanged content already available in the same context; after truncation or a lost result, read the missing ranges in bounded outputs. Fresh workers and changed authority/candidate bytes still require their own current evidence.

## Platform and evidence discipline

Pipeline and skill defaults are platform-neutral: they do not assume or prescribe a particular operating system, browser, runner, or interactive tool. A platform-bound choice is permitted only by explicit user-approved product authority or observed project or runtime capability supported by current evidence. Before a platform-bound command or scenario, discover relevant available tools and probe the intended target through a safe read-only check. Failure of one API or UI channel does not prove the environment unavailable: check an already available specialized connector or other permitted channel before declaring the required capability unavailable. Do not invent tools, change the authorized target, bypass project rules, or repeat the failed probe without new evidence. Apply the shared technical assessment and record the resolution, including a successful alternative. If the required capability remains unproven, fail closed and record the minimum recovery action.

Evidence proves only the path exercised. A fixture, test double, structural check, or passing aggregate does not prove the approved user scenario through its actual integration. Engineering and QA must identify that distinction in their semantic result and verify the reported defect through the assigned production path when available. An unexecuted mandatory scenario remains unverified; a reproduced product or test failure is `fail`, not an environment `blocked` result.

Engineering and QA may use computer control and the tools actually exposed in their environment: discover and verify a suitable editor connector, native computer, browser, or CLI against the authorized project/session. Engineering may make necessary editor changes only within the assignment's persistent write paths and project editor ownership rules. QA's read-only boundary covers persistent product files, not temporary gameplay: it may run the assigned play sessions, inputs, UI actions, and console observations. Coordinate one owner for a shared editor/player session, restore only test-owned temporary state, and do not close, overwrite, or terminate unrelated user work. Permission is not proof of tool availability; the Director includes these rights and observed capabilities in the worker handoff. Controller-owned planned argv still run only through `complete`.

Before an action with persistent or external effects, establish its actual effect, target and destination from the relevant current tool or application state and compare them with the existing authorization and write scope. An action title, shortcut, API name or matching session identity does not establish the write destination. When a default route is ambiguous, inspect it or use an explicit in-scope route before acting; do not infer permission for an external write from a local-edit task.

Preserve valid earlier user authorization, including authority passed through the Director. A native confirmation dialog does not by itself require new user permission for that same authorized action and destination. Apply the actual governing instruction under the instruction hierarchy; distinguish a native warning, your interpretation of a rule, and an actual approval-review rejection. Report a rejection only when a tool returned one, with its stated reason. A genuinely new effect outside existing authority or an unresolved governing conflict uses the existing blocked route.

In the existing handoff, preserve each constraint's source and scope: direct user instruction or approved authority, Director setup decision, or observed capability. Do not promote an assistant's prior restriction or a failed capability probe into a user prohibition. Correct unsupported attribution without discarding a current scope restriction; only its authorized owner may revise it.

An environment still unavailable after the shared technical assessment is a terminal `blocked` result with `user_input_required=true`, not a retry state. Workers and Directors MUST NOT retry the same unavailable environment. This terminal rule does not prohibit evidence-led diagnosis and permitted alternatives before that determination. The recovery route opens only after authority or capability evidence changes and resolves the recorded prerequisite; then read public `status` and execute its exact same-run `init` action. The controller records the terminal history, preserves retained candidate paths and the current journal, clears phase credit, and restarts at Plan; there is no separate archive or resume operation.

For a reported authority/scope conflict, the responsible authority may resolve the prerequisite by accepting a source-grounded diagnosis bound to the current candidate and approved inputs that disproves the conflict and identifies a sufficient correction within the unchanged contract. Record that determination in the existing handoff before using `status` -> `init`. It does not claim an environment change, authorize a speculative retry or weaken approved obligations; a remaining conflict still requires the ordinary upstream resolution.

Pipeline-observation workers report every issue observed within their assigned observation scope, including independent issues found after the first failure, and verify the evidence before concluding. The pipeline-maintenance observer ledger classifies its issues as `pipeline`, `test`, `product`, or `environment`. Review and QA instead stop at their bounded stage contracts: Review reports only findings eligible under its controller-derived `review_target`, while QA records only assigned acceptance checks and a real blocker when applicable. Review and QA remain read-only. After a new explicit user command starts a separate pipeline-maintenance task, its observer first preserves the minimal reproduction, then adds a compact regression and makes the smallest simplifying pipeline-only change before focused and adjacent regression runs.

The worker stops after returning its artifact. The Director validates it through the controller and decides the next transition. Only controller state records pipeline progress.

## Director child-result consumption

After spawning any phase worker issued by the runtime, the Director owns that exact child until its terminal result and MUST wait using the available coordination primitive. The Director MUST NOT send a final response, claim `work continues asynchronously`, or otherwise relinquish the turn while that child is live.

After the child reaches a terminal result, the Director MUST re-read public controller status, prove that the same active assignment owns the exact returned output artifact, execute that assignment's exact public controller `complete` action including for a blocked outcome, and re-read the resulting public controller status. With no child owning an active assignment and no completed child artifact remaining unconsumed, execute the resulting authorized `next_action`; an available `accept`, `next`, or Director decision is still work in this run. Finalize only on the controller's terminal result, a genuine unresolved user prerequisite, an explicit user stop, or the incident/context handoff required here. Report an assignment as issued only when it exists in `active_assignment`; a proposed assignment in `next_action` is pending.

## Artifact format correction

For runtime assignments, the issued `active_assignment.artifact_schema` is the sole field/type contract. Give it and the exact output path to the worker unchanged; role examples illustrate minimal results, not extra fields. Before returning, that worker parses its JSON, checks required/allowed keys and item shapes against the issued schema, omits empty optional fields, and includes non-empty `blocker` and `required_action` only for `blocked`. For Slicer records, return only their three caller-owned keys; sealed `read_paths` are controller-owned. Planning analysts instead use their own controller's mode choices and result contract.

If `complete` rejects only artifact format and fresh status confirms the same active assignment, return the exact error to the same worker to correct only its output file, then consume it through the same assignment. Do not rerun its product work, create a new role, or replace a failure with a blocker to repair JSON. A new assignment still requires a fresh worker; if ownership changed, follow current status instead. Controller validation remains authoritative.

`questions` contains only reversible technical clarifications within consistent approved authority, and is allowed only on a passing result. Resolve an authorized technical correction under the shared policy rather than disguising it as a product contradiction or adding a question to a failing result. A remaining product/scope/authority contradiction instead uses the existing `blocked` outcome with the exact conflict in `blocker` and user-owned decision in `required_action`; never send it to the Director's technical-assumption channel. The user chooses a targeted local amendment through the responsible stage owner or a broader upstream revision; a local amendment still receives the required exact-source approval and sanctioned runtime reconfiguration. Mixed `fail`/`blocked` plus `questions` is rejected rather than silently dropping the question.

## Controller incident stop

If any Director or worker suspects a defect in the pipeline controller, runtime, skill, protocol, or controller-owned state transition, it MUST immediately stop the product run. It reports the failing public action, phase/generation, bounded and redacted error evidence, observed versus expected behavior, candidate impact, and the exact recovery prerequisite. It MUST NOT edit, patch, bypass, monkeypatch, locally replace, or continue through the pipeline implementation, instructions, state, or checks.

Product-run authority never grants pipeline-maintenance authority. Pipeline maintenance may begin only as a separate task after a new explicit user command that names that maintenance work. Until then the run remains stopped; no worker assignment or product lifecycle transition may continue on a locally altered pipeline.
