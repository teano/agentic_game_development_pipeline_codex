# Interaction and evidence

Read the named section for the actual event. The project supplies its tools, commands, prerequisites and expected behavior; this contract supplies no engine or platform defaults.

## Environment actions

Pipeline and skill defaults are platform-neutral: they do not assume or prescribe a particular operating system, browser, runner, or interactive tool. A platform-bound choice is permitted only by explicit user-approved product authority or observed project or runtime capability supported by current evidence. Start with the supplied approved/setup tool, executable, resource and target locators. For QA, first select the approved method and [agree its actual execution route](qa-acceptance-contract.md#agree-the-execution-route); a general tool listing is not a prerequisite to using a confirmed route. Use its permitted invocation and retain the actual result. A missing locator or actual failure opens targeted discovery through [technical assessment](technical-decisions.md#resolve-before-escalating), including another already available permitted channel when compatible with the approved method. Resolve a producer mismatch with the existing responsible owner before switching; do not reinterpret a generic probe as a product invocation. A security denial applies to its stated outcome and scope across tools and later runs. Preserve it; discovery cannot authorize a bypass. If the required capability remains unproven, fail closed on affected work and retain the precise missing prerequisite and minimum recovery action.

Engineering and QA may use computer control and the tools actually exposed in their environment through that supplied route or justified discovery. Engineering may make necessary editor changes only within the assignment's persistent write paths and project editor ownership rules. QA's read-only boundary covers persistent product files, not temporary gameplay: it may run the assigned play sessions, inputs, UI actions, and console observations. Coordinate one owner for a shared editor/player session, restore only test-owned temporary state, and do not close, overwrite, or terminate unrelated user work. Permission is not proof of tool availability; the Director includes these rights and observed capabilities in the worker handoff. Controller-owned planned argv run through active Engineering/QA `check` or terminal `complete`; a worker may invoke only the explicitly granted native-check route while quiescent, otherwise it requests the Director relay, and it never executes argv itself.

Before the dependent behavior, identify its external data, participants and resources, the actual permitted read/create/update/publication channels, and what must already exist for a real run. A local fixture or injected value proves only its isolated case; it does not establish that external configuration or publication exists. Inspect the relevant available channel, not the entire environment. Preserve a tool denial while using another already available permitted channel when appropriate. Once a missing prerequisite is resolved, supply its exact evidence to the existing narrow recovery route instead of replanning unchanged work.

## Permission and capability boundaries

Before an action with persistent or external effects, establish its actual effect, target and destination from the relevant current tool or application state and compare them with the existing authorization and write scope. An action title, shortcut, API name or matching session identity does not establish the write destination. When a default route is ambiguous, inspect it or use an explicit in-scope route before acting; do not infer permission for an external write from a local-edit task.

Preserve valid earlier user authorization, including authority passed through the Director. A native confirmation dialog does not by itself require new user permission for that same authorized action and destination. Apply the actual governing instruction under the instruction hierarchy; distinguish a native warning, your interpretation of a rule, and an actual approval-review rejection. Report a rejection only when a tool returned one, with its stated reason. A genuinely new effect outside existing authority or an unresolved governing conflict uses the existing blocked route.

In the existing handoff, preserve each constraint's source and scope: direct user instruction or approved authority, Director setup decision, or observed capability. Do not promote an assistant's prior restriction or a failed capability probe into a user prohibition. Correct unsupported attribution without discarding a current scope restriction; only its authorized owner may revise it.

An environment still unavailable after the shared technical assessment is a terminal `blocked` result with `user_input_required=true`, not a retry state. Workers and Directors MUST NOT retry the same unavailable environment. This terminal rule does not prohibit evidence-led diagnosis and permitted alternatives before that determination. The recovery route opens only after authority or capability evidence changes and resolves the recorded prerequisite. Use `recover-capability` for its guarded unchanged-input case; otherwise follow the exact public recovery binding described in the protocol. Retain only controller-proven unaffected credit; neither repeated availability probing nor a journal entry resolves an unchanged prerequisite.

For a reported authority/scope conflict, the responsible authority may resolve the prerequisite by accepting a source-grounded diagnosis bound to the current candidate and approved inputs that disproves the conflict and identifies a sufficient correction within the unchanged contract. Record that determination and its applicable authority in the existing handoff before the matching public recovery action. It does not claim an environment change, authorize a speculative retry or weaken approved obligations; a remaining conflict still requires the ordinary upstream resolution.

## Evidence sufficiency

Evidence proves only the path exercised. A fixture, test double, structural check, or passing aggregate does not prove the approved user scenario through its actual integration. Engineering and QA must identify that distinction in their semantic result and verify the reported defect through the assigned production path when available. An unexecuted mandatory scenario remains unverified; a reproduced product or test failure is `fail`, not an environment `blocked` result.

Inspect the actual visual when its appearance/state is part of the criterion; a screenshot locator is not inspection. Retain the frame and case locator outside context, emit the necessary image through the host's image display once, and reopen it only when assessment or restoration needs it. Do not repeatedly print retained frames or serialize image/base64 envelopes into text alongside already consumed observations.

For a mandatory integration claim, controlled raw inputs and observation wrappers may preserve real behavior. Replacing an inner production policy or resolution stage proves only that boundary, even when the outer entry point runs. Assert the required observable state, effect, or accounting; returned descriptions alone do not prove a separate underlying effect. When returned data are themselves the required output, verify those actual data under that contract. This preserves valid boundary tests and adds no obligations beyond the existing mandatory claim.

Before calling an automatic gap mandatory, distinguish the required observable property from an explicitly required executed scenario or method; do not transfer a manual witness format into an AUTO check. For an observable property, compose the already executed candidate tests with a verified bounded proof of their shared production path, rather than requiring the same assertion in every related scenario. An acceptance gap must remain after that composition or identify an unexecuted explicitly required scenario; one hypothetical mutation or a locally absent assertion is insufficient. A bounded proof cannot replace explicitly required runtime/manual execution, and an inner substitution remains boundary evidence. A self-checking predicate needs independent real checks or bounded source proof of its correctness, not its own success alone. Optional strengthening stays optional and does not create rework.

Explicit scenario or case wording remains an execution obligation when its approved applicability holds; implementation symmetry or proof of an observable property does not cancel it. Determine applicability from the approved contract and its material input/property distinctions, not from the current implementation alone. If approved sources leave applicability unresolved and that changes the verdict, obtain one bounded clarification from the existing responsible specialist through the existing nonterminal question/control-return route while the assignment remains active. Do not issue a clear terminal pass or encode a verdict-changing question as a pass artifact before that answer. Genuine authority or capability-denial blockers keep their existing routes.

Derive expected observations independently from the authority, a permitted oracle or an invariant with verified premises, not the same decision being tested. For a claimed case, establish its material premise in the actual state/input when the relevant action occurs, through the fixture/setup, helper and production trace. Earlier setup alone is insufficient if an intervening transition removes the distinguishing property. Use a decisive premise check where needed, or sufficient exact bound execution/source proof; do not demand new instrumentation to expose an already proven premise. A test name or ID is a locator, not proof that its case ran. Shared observations may support several IDs only after an independent mapping to each required result.

Compare the decisive observed values, state, geometry, output or effect with that expectation. An executed command, changed object, named animation or successful API response proves only that action unless its result is the approved observable criterion. Contradictory evidence excludes PASS even when the operation or surrounding suite succeeded; insufficient observation remains unverified. Do not replace a discrepancy with a narrative of the intended behavior.

An always-applicable obligation to inspect a conditional policy and assess reachability can be satisfied by the permitted composed proof even when the hypothetical output is unreachable under a governing priority. Credit the actual executed paths and exact source invariant; do not demand an impossible fixture, fake legal inputs, a new helper or instrumentation merely to expose that output. This is distinct from a genuinely conditional assertion whose approved condition is proved false: only that assertion may become `not_applicable`, without claiming execution.

## Compare automated acceptance with test assertions

Engineering performs this comparison before its terminal handoff; Review independently performs it for the issued product target before its first substantive verdict and for affected obligations after repair. Use the existing approved source/QA definition, coupled tests and retained execution records; this is work inside those roles, not a new coverage document or a substitute for independent QA.

1. Select a coherent behavior from the existing mandatory automated assertion IDs. Read each required precondition, action, observable result and approved proof method, including variants and permitted composition. For a compound expected result, separate its necessary conjuncts for this assessment; this does not create another inventory or artifact.
2. Open the coupled test bodies and relevant helpers. For each conjunct, establish under [Evidence sufficiency](#evidence-sufficiency) that the material premise holds at action time, trace the exact production path, and identify the decisive assertion that would fail if that property alone were wrong. Equality on inputs lacking the relevant attribute does not exercise its preservation; finding one expected output does not establish required uniqueness. Use that counterexample to examine the assertion's reach, not as a product defect or sufficient gap finding by itself. A shared assertion helper may establish the result when its real checks and premises do.
3. Join that source inspection to the current bound execution record: which exact cases ran, on which candidate, with which substitutions, and what result they captured. Assess permitted composition or an approved alternative method against the whole required observation and its applicable variants; unrelated scenarios, test names and a green aggregate cannot supply a missing conjunct. Credit sufficient shared proof without duplicate assertions or execution, while retaining explicitly required executed scenarios.
4. For an uncovered mandatory observation, locate existing proof or a permitted check before concluding it is absent. Engineering closes a correctable in-scope test/proof gap; Review reports an evidenced gap through its existing finding contract. Put decisive test/assertion and execution locators in the existing result/finding as needed. Leave later assigned manual/device observations unverified.

## Preserve execution evidence

Finish the checked source and behavior-defining documentation before fixing the candidate for a run. Capture its actual binding and relevant environment state before execution, preserve the raw response when received, and capture the required after-state before another mutation. Never reconstruct a missing before-binding, console result or observation from memory. A later run or cleared console must not erase the independent reader's source.

Keep execution records and terminal reports in their authorized workflow/control locations outside the candidate. This is not an exemption for Markdown: requirements, normative documentation and other governed content remain part of the candidate. A meaningful checked-content change invalidates affected proof; writing its outside-candidate record does not require repeating the run. Several assertions may refer to one retained execution record with exact case/observation locators, provided each mapping actually proves its criterion. Shared launch details are recorded once; assertion outcomes, methods, reasons and observations must agree with that record.

## Local tool recovery

Use the public operation's structured argv/input schema and documented reader/writer. Keep large payloads in files rather than interpolating them into shell source. Retain the host result and deserialize once at the tool boundary; work with its actual object/string type instead of guessing nested envelopes. Select relevant properties or a source section before serializing for display. For example, in PowerShell `$record | Select-Object invocation, environment | ConvertTo-Json -Depth 12` selects those fields first; `ConvertTo-Json | Select-Object -First 1` serializes the whole object and does not select its semantic content. Keep the complete raw result in its authorized evidence location. For a chosen dependency establish its relevant availability, then use an already permitted available route; an absent optional convenience does not justify environment-wide discovery.

Distinguish a request that never executed, an executed action whose result could not be read, and an operation that failed. Correct a local argument/format error with the same owner; recover saved output for a committed action instead of repeating its side effect. Preserve actual uncertainty and the public replay binding when completion is unknown. A typo or serialization failure creates neither product rework nor a new stage; real scope, authority and security denials retain their existing routes.
