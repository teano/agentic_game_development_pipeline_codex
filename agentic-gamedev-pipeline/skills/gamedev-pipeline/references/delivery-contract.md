# Assignment and source delivery

Read for an issued runtime assignment. These transport commands do not change product authority, role ownership, write scope, acceptance or the controller's phase sequence. Use the existing launcher with global `--root <project-root> --feature <slug>` before the command; obtain exact flags from command help. Directors use global `--brief` before `status` and technical/mutation subcommands: it retains action/lifecycle/recovery metadata without printing the full assignment. Full public output remains available explicitly when its content is needed; do not routinely ingest it before exporting a delta.

## Prepare the working input

`access.read` is the permitted research boundary, not a request to load every file. The assigned specialist selects applicable requirement sections, code targets, affected external contracts and decisions from the approved task and authorized sources; it preserves governing general requirements, mandatory findings/checks, exact Review target and every QA identity. Uncertain relevance requires specialist investigation, not omission. The Director forwards complete assignment delivery and exact approved/task/specialist-supplied source/version locators without reading code, diffs, tests or document bodies to curate semantic relevance. Project instructions govern their environment rules; this pipeline supplies no engine defaults.

Use `assignment-export --input <exact-project-relative-path>` for starting sources already selected by the approved task or specialist. Selection is separate transport metadata; the assignment remains unchanged and other authorized sources remain available through `file-read`. Empty selection waives nothing and does not request the whole read scope. The selecting specialist supplies section/requirement IDs and purpose where needed; the Director forwards these unchanged and does not infer obligations from filenames or make a script invent relevance.

The export returns immutable packet and delivery-response digests, its bound absolute `project_root`, `assignment_id` and `worker_id`, a locator and `working_set` metadata: packet/transport/selected-source bytes, source count, estimated tokens and section/technical-decision indexes. `estimated_tokens` is a bytes/4 planning estimate, not actual session context or billed usage. `context_sections` and `technical_decision_index` expose exact pointers for selecting relevant complete fields; the runtime does not decide semantic relevance. When the active assignment, sealed current slice and approved plan source still bind, `verification_exit_criteria` adds the plan `path`, raw-byte `version` and character length; its optional `section` gives only the exact heading range for that slice. Use `file-read` with that version from `start_offset` through `end_offset`; `file-read.complete` still refers to the full source. If the exact section is unavailable, the same source locator remains a full-source route; unavailable metadata never waives an approved obligation. The canonical full packet remains lossless. A locator is not delivered knowledge. The receiving worker must read the assignment, applicable constraints and complete required evidence before work or judgment. Keep user permissions, observed capabilities and owner/model constraints outside the immutable assignment; only actual user/stage authority supplies them.

## Read without loss

Native export and assignment-issuing `step` also return `dispatch` (`pipeline-dispatch-v1`), a ready-to-forward description rather than another semantic packet. It binds run/feature/generation, logical worker/assignment/role, absolute `project_root` and `cwd`, the running bundle's separate `launcher_argv` and global `controller_args`, role-instruction locator, absolute full/delta input paths/digests, full-packet fallback, scope/schema pointers and exact absolute/relative output. `allowed_action` is `execute_issued_assignment`; `stop_boundary` is `terminal_artifact_or_required_control_pause`. An informative check event under an active grant is not such a pause: consume the full refreshed delivery and continue authorized work in the same host turn under [active checks](execution-contract.md#check-inside-active-engineering-or-qa). `output.write_authority: issued_exact_terminal_artifact` records the issued assignment's permission to write only that output, including read-only Review/QA. It does not widen product `access.write`, authorize other control/state/history/Delivery writes, or grant controller commands. `controller_mutation_authority: requires_separate_bounded_grant` applies to controller-command mutation, independently of this terminal-output right. Host owner, control correlation, actual permissions and any bounded native check grant remain caller metadata; no descriptor creates a check grant. Forward it unchanged; do not copy its fields into a newly authored assignment or read its semantic payload in Director. The worker resolves its scope/schema pointers in the complete packet and consumes the required input before work. A delta is usable only against that same recipient's retained complete applicable baseline; the full packet remains the fallback when retention is lost. No descriptor or locator is proof of reading, completion or PASS.

Stable resource locators may cross agents; session-local tool handles are not presumed transferable. The assigned specialist establishes its own binding using the authorized capability and reports any actual failure through the shared control return.

`delivery-read --digest <response_digest> --offset <offset> --limit <size>` reads the exported response in Unicode-character pages. Follow `next_offset` until `complete` is true. `--pointer /assignment/context/technical_decisions` may select one exact JSON section; its `complete` applies only to that section, not the full assignment. Use section reads to deliver required fields without replaying unrelated packet fields. The complete packet already exists at the returned immutable path; do not rewrite it or guess missing JSON from a page boundary. Read the full required semantic fields, even when they take several pages.

For Codex `functions.exec`, the whole batch shares its outer output budget: large nested `exec_command.max_output_tokens` values do not increase it. Set the outer first-line directive, for example `// @exec: {"max_output_tokens": 8000}`, and keep the combined reads plus response metadata within that budget. Emit `text(result.output)` instead of serializing the shell-result envelope. If the selected material exceeds the combined budget, use separate bounded reads; repeating an oversized batch with larger nested limits still clips the outer response. A source page marked `complete` inside a truncated tool response is not delivered knowledge: retrieve the missing range before relying on it.

For Director instruction reads, follow [bounded plain-text pages](director-runtime.md#read-instructions-without-clipping): one needed section/page, retained path/hash/offset, no serialized batch of manuals. An exact routing-row lookup uses bounded `rg -n -F` for its unique label, without overlapping before/after context objects. Already delivered unchanged `next_action` remains usable at terminal consumption; only a missing/stale action after actual cursor change needs status, not every partial final wrapper.

`file-read --path <literal-project-relative-path>` reads a selected authorized UTF-8 source and returns its raw-byte version plus exact character range. Supply that `--version` for continuation pages and for any read intended to refer to those same bytes. If the source changes, the old version fails; obtain the current authorized source and reassess affected conclusions. Binary sources need the project's appropriate reader, not conversion of binary bytes into text tokens. The reader does not grant new file access, follow escaping links or read another workflow.

Do not reread complete unchanged content already delivered to this recipient's current context. After a fresh worker, context loss, source change or an incomplete output, retrieve what is actually missing. A packet digest proves identity, not that the model consumed its bytes.

## Update the same worker

For continuation, including remediation under a new assignment ID with the same owner alias, retain the eligible physical owner and export with `--baseline <prior_packet_digest>` only if that same recipient actually received the complete relevant prior content and still retains it. A new role alias or replacement physical worker receives a full export. The delivery response describes changes and the target full-packet digest. Consume every change, including removals and changed assignment/output IDs, before continuing. This also applies after an explicitly granted same-owner native `check`: export and fully read its delta before resuming, or read a full current packet when the exact baseline is unavailable. Within that unchanged assignment/caller grant, consumption and the next authorized work remain in the same host turn; sending its informative result does not require a new dispatch or acknowledgment. Brief diagnostic metadata, a locator/digest, or CLI exit 0 does not deliver complete results, pending checks, changed instructions, or decisions. Keep the latest cursor and immutable transport locators outside the terminal semantic artifact. The full target packet remains independently readable if reconstruction is uncertain. A fresh worker uses a full export; never pass a delta against another worker's context.

Use an eligible known recipient's baseline on the first export. Reuse returned delivery, except that a full `step --through-handoff` delivery for an eligible continuing owner permits one baseline export and delivery of only that delta. `step` has no baseline argument. Do not read/deliver both payloads, re-export for identity or resend unchanged material. Retention acknowledgment accompanies only the next necessary [control return](control-return.md); it never creates a separate ping. The worker consumes required semantic pages; the Director does not read them first.

Required findings/checks, current technical decisions and operative answered questions are lossless. Their preview, hash or omitted-count marker cannot substitute for full content. Current journal data is canonical; stale or legacy truncated context must be restored from its matching authority source or reported unavailable, never treated as a complete assignment. Updating one record does not create a second journal or authorize new scope.

## Mechanical controller actions

`step --expected-generation <generation> --action-id <status.next_action.command_id>` consumes one exact public mechanical `next`, `complete` or `accept`. It reuses the controller's validations and action identity. Repeat the same action identity after an uncertain response; do not switch to a new one merely to retry. It returns compact state and assignment-export metadata rather than full history, plus a typed outcome (`assignment_issued`, `phase_passed`, `phase_failed`, `gate_failed`, `blocked`, `accepted` or `replayed`), current `next_action` and bounded failure data where applicable. `result: executed` alone is transport success. Use the returned fresh cursor instead of immediately repeating status; refresh on missing/stale binding or evidenced external change.

Before `complete`, the Director must independently establish child termination, assignment ownership and the exact returned artifact. File existence is not child-liveness evidence. A missing artifact causes a stop, not a fabricated result. A semantic question, recovery fact, ready phase or terminal state remains the Director's existing route; the helper does not answer, authorize, reconfigure, publish or waive checks. Workers do not execute `step` or controller-owned planned commands. Read [Director lifecycle](director-runtime.md) only when acting as Director.

Optionally add `--through-handoff` to continue a passing `complete` through `accept` and `next` (at most three actions), or start at either remaining action. It stops at the first new assignment, missing artifact, semantic/gate failure, blocked result, question, recovery, ready boundary or replay. It never consumes the new worker's output. The response preserves the original retry identity in `request`, lists only actions actually executed in `steps`, and returns the final cursor/delivery. These are separate validated transactions: an error may leave earlier actions applied. After any uncertain response, retry the original `request`; replay of that original request changes nothing and reports the current cursor/assignment with an export command when needed, without claiming the whole chain ran. If a later action was already applied concurrently, the call stops there and `steps` can still contain this call's earlier executed actions; `outcome: replayed` alone does not mean the whole call made no changes. Establish termination/quiescence before starting `complete` exactly as above; this option supplies no liveness or semantic authority.
