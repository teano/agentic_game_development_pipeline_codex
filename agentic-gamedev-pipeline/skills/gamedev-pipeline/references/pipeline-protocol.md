# Pipeline v2 protocol

This is the complete Director protocol for the sole runtime engine.

## Authority and phases

Apply the shared [technical decisions](technical-decisions.md) policy. Approved source files remain immutable within an authority epoch. Their exact paths and planned checks seal the base contract; a controller-admitted active-Engineering technical decision may add exact incidental file paths or reorder the same planned argv without changing product authority or acceptance. In assignment rules below, current slice access and command order mean that controller-derived effective execution contract. Initialization and upstream source equality still use the unchanged approved base. Neither free-form journal text nor caller-authored assignment changes grant an overlay.

Approved requirements, specification, and development plan files are immutable authority for an authority epoch. `init` accepts exactly the authority keys `requirements`, `specification`, and `plan`, one compact safe ASCII run identifier, and at least one caller slice record with exactly `id`, `allowed_paths`, and `planned_commands`. For initial `init`, the Director serializes already-approved verification methods into `planned_commands` argv using existing applicable repository tools and rules; the approved plan need not contain a literal argv block. Serialization alone does not change execution authority: preserve approved methods, scope, and mandatory checks, and diagnose missing tools or failed prerequisites separately. For each slice, the controller parses the approved plan's ordered `Owned Paths`, requires it to exactly equal ordered `Scope Contract.editable_paths`, and requires caller `allowed_paths` to be byte/order-identical; narrowing, broadening, duplicates, invalid paths, and reordering fail closed. The controller separately derives and stores the fourth `read_paths` field from Context Capsule `authority_paths` plus `evidence_paths`; IDs must match exactly, paths are deduplicated canonical project-relative exact or terminal `dir/**` rules, every disjoint `Expected Paths` entry must be covered, and caller-authored read scope is rejected. `allowed_paths` remains the sole write authority; no specification semantics are inferred. The run ID starts and ends alphanumeric, is at most 64 characters, and otherwise permits only dots, underscores, or hyphens. The same command can rebind changed approved authority or an old three-key live scope under generation CAS, restart planning, and retain the prior candidate/history as audit context. Sole runtime v2 has no `authority_recovery_hold`: a sanctioned upstream controller may reopen its own authority, after which `status` observes authority and checkout under the state lock and returns one exact `init` whose command ID binds the observed authority paths/bytes and controller-projected four-key slices. Execution recomputes and validates that binding under the lock; every other public mutation fails closed, and every replay fails closed, on drift or an old unsealed scope without a state write. Execute that `init` only after every changed upstream controller reports readiness for the exact current bytes; unsanctioned drift must be restored or reconciled upstream first. An active assignment may be interrupted only after the controller proves its checkout diff stays within the old assignment; pre-existing foreign drift yields the non-mutating terminal status `checkout_recovery_required` instead of an unusable `init`, and the fresh Slicer scope must cover retained Engineering paths from blocked candidates and active interruptions across reconfigurations. Separately authorized runtime maintenance can rebind an idle run through the same explicit `status` → `init` route: the command ID additionally binds the observed runtime digest, the checkout and history are retained, and stale phase credit is cleared. Runtime changes with an active assignment and every normal mutation on a stale runtime remain forbidden. Authority path comparisons follow host filesystem case semantics, so spelling aliases never turn sanctioned authority drift into foreign checkout drift. Never edit controller state directly.

A suspected controller, runtime, skill, protocol, or state-transition defect is a mandatory incident stop. The Director and every worker stop the product run, publish bounded redacted evidence and the exact recovery prerequisite, and do not edit, patch, bypass, replace, or continue through the pipeline. Product-run activation is not maintenance authority. Only a new explicit user command may start a separate pipeline-maintenance task.

The seven phases are `plan`, `slice`, `engineering`, `review`, `qa`, `docs`, and `ready`. The controller derives every transition. Each ordered slice passes Engineering, fresh Review, and fresh QA before the next slice; documentation starts after the final slice. A passing phase is committed with `complete` and advanced with `accept`; a question returns to the phase that produced it, while `blocked` terminates the phase with `user_input_required=true`. It cannot be retried in place. After the recovery prerequisite is resolved under the [shared stage-handoff invariant](stage-handoff-invariant.md), public `status` returns one exact same-run `init` that records the terminal history, preserves retained candidate paths, clears phase credit, and restarts at Plan. Documentation changes must pass a fresh Review and QA before `ready`.

An explicitly authorized prerequisite baseline can be adopted by existing `init` after the first genuine Engineering `blocked` result, before product work. Admission requires no active assignment, one initial epoch and exactly one completed Engineering attempt, only Plan/Slice/Engineering records whose controller base/candidate trees equal the initial baseline, empty changed paths/violations and no controller failure. Current approved authority passes its source-chain validator, including any sanctioned fully reconverged revision; repository policy stays unchanged; the proposed candidate must be a clean committed Git tree. Both `status` and `init` enforce this boundary. The existing action binds the fresh tree, generation, authority, slices and runtime; same-tree HEAD metadata is not a separate identity. A commit alone is not user authorization. Successful init preserves the old candidate and terminal history as audit context, records the new non-credit baseline and restarts Plan. Dirty state, later/reconfigured runs, active work and retained product changes do not gain this exception; their existing fail-closed behavior remains.

## Commands

- `init`: create a v2 run, or reconfigure changed approved authority/scope/runtime at a safe boundary.
- `status`: read the compact current view and its one controller-derived `next_action` without mutation.
- `next`: issue one bounded assignment for the current phase, deriving its canonical identity, task, access, checks, and Review target from controller state; compatibility identity flags may be omitted and must match exactly when supplied.
- `complete`: submit one semantic worker artifact; controller evidence is gathered independently.
- `answer`: record the Director's safest reversible authority-consistent assumption and invalidate the affected artifact.
- `accept`: advance from the current passing artifact.
- `migrate`: retained fail-closed tombstone; schema-10 migration is unsupported by `git-tree-v1`, so archive legacy state/findings and run fresh Plan/`init`.
- `ready`: seal the live, independently reviewed and tested terminal candidate.
- `technical-observe`: capture a clean scoped before-action checkout observation for the active Engineer.
- `technical-decision`: bind a current technical decision and bounded execution adjustment to that same active assignment and observed checkout.

Exact flags belong to each command's `--help`; do not copy old command recipes into worker prompts.

## Technical action interface

Only active Engineering may request these two actions; the Director executes them while the same Engineer remains the sole product writer. Read fresh `status.technical_actions` for the expected generation and observed tree, including when ordinary `next_action` reports checkout recovery. Use `technical-observe --id <command-id> --expected-generation <generation> --action <description>` before an editor/tool action that can produce persistent incidental changes. A valid scoped tree is required. The resulting `active_assignment.technical_observation` binds its ID, tree, action, and assignment; an observation made after foreign drift cannot establish its origin.

The Engineer may write the bounded request only to `.agentic-pipeline/Workflows/<feature>/technical-decision-request.json`, separate from candidate files and its terminal semantic artifact. The Director submits it with `technical-decision --id <command-id> --expected-generation <generation> --packet <request-path>`. Required packet fields are `assignment_id`, the fresh `observed_tree_oid`, and `entry` in the shared journal shape. Optional `additional_paths` lists exact files, never broad patterns; `command_order` is a non-empty permutation of the unchanged planned argv list; `observation_id` binds reconciliation to the earlier controller observation. Omitted adjustment fields retain this entry's existing adjustment. Explicit empty `additional_paths` removes it only if remaining governed scope still covers actual changes; explicit empty `command_order` is invalid. The caller creates a unique command ID for these two explicit actions; assignment, tree and observation identities come from current controller evidence, never narrative guesses.

For unexpected checkout changes, first establish their cause and effect. Reconciliation admits exactly the foreign paths arising after the saved observation and covered by the requested exact-file adjustment; pre-existing foreign drift and known unrelated/user changes remain excluded. The observation and sole-writer discipline support provenance but do not prove that an unrelated concurrent writer did not act. If provenance is unresolved, use the existing recovery route. A file type or normal editor behavior alone is insufficient evidence.

After success, read current status and send the refreshed assignment identity and output path, journal reference, and relevant current entries to the same physical Engineer session before further mutation. Do not retain the old generation, access, or command order. An ordinary technical operation reorder inside existing access does not require a controller action; include its decision in the terminal semantic artifact. A public technical action never weakens tests, admits product choices, changes approved technology, edits authority, or grants ready credit.

Every runtime role may submit current `technical_decisions` entries through its issued artifact. They replace the same ID in the feature-local current journal and cannot supply sealed execution fields. Existing execution adjustments remain controller-owned. Review/QA corrections requiring changed implementation or execution use ordinary `fail` remediation; a passing entry describes the candidate actually assessed. Journal changes require freshness checks and renewed affected phase verification before acceptance, never credit based on an older record. `init` and reconfiguration preserve the current journal. Reentered upstream stages consume it through their shared read-only interface; a user-approved local authority amendment uses the owning stage's targeted revision/approval and ordinary runtime reconfiguration, without requiring full document regeneration unless needed or requested.

Mutating `init` validates the approved PRD, the specification's exact PRD trace, and the plan's exact PRD/specification traces using the existing Planning parsers. It reads no additional stage-state registry. `status` remains read-only and exposes recovery while upstream documents are being reconverged.

The Director executes `status.next_action` for ordinary lifecycle work and the bounded `technical_actions` interface for an active Engineering request; it does not invent generations, assignment identities, output paths, access rules, checks, Review targets, question IDs, or recovery reasons. Every invocation supplies exact `--root` and lowercase `--feature`; the controller derives `.agentic-pipeline/Workflows/<feature>/pipeline-state.json`, rejects foreign/escaping/linked bindings before mutation, and never scans or changes a sibling workflow. `controller_decision` actions include a policy for choosing a conservative authority-consistent technical assumption without unnecessary user bookkeeping; product choices remain user-owned.

## Assignment and artifact boundaries

Only one assignment may be active. It exposes a controller-derived `artifact_schema` and one controller-derived `output_path` under `.agentic-pipeline/Workflows/<feature>/outputs/`; the worker follows that schema without reading runtime code, writes its semantic JSON only there, and `complete` reads only that exact path. Controller and history paths may remain Git-tracked; tracked and untracked control paths are excluded before live worktree staging can open them and remain absent from candidate evidence, while non-control authority, product, and repository-policy drift remains governed, so semantic output cannot create candidate drift. Every staged or policy path passes the same effective candidate classifier: tracked and non-ignored non-control policies remain governed, an ignored policy remains governed only while its parent is Git-traversable and it can hide otherwise candidate-visible paths, and policy inside an already ignored subtree stays outside with the other ignored editor or cache bytes. Every newly issued assignment uses a worker ID absent from controller-owned completed actor history, and Engineer IDs cannot be reused for Review or QA. A rejected output format with the same active assignment uses the shared same-worker artifact correction rule; it is not a new assignment. The controller derives canonical read/write access, checks, and Review target again for every `next`; omitted or conflicting caller values never change the issued packet. Planning, slicing, Review, and QA receive no candidate write access. Engineering scope and checks come from the current slice. Documentation receives controller-derived project-relative write paths. Authority files are never writable.

Workers run only the scenarios supplied by the assignment. Engineering, Review, and QA read access is the deterministic deduplicated union of authority plus every completed/current slice's `allowed_paths` and sealed `read_paths`; a post-Docs Review also reads its exact changed Docs target paths. Engineering write access and Engineering/QA checks remain exactly the current slice's `allowed_paths` and `planned_commands`, and future slices remain unreadable. Review read access outside the target is evidence context, not audit scope. For `current_slice_implementation`, the small controller-derived `context.review_target.required_scope` equals `current_slice.allowed_paths`, while `candidate_changes` lists accepted Engineering controller changed paths plus retained Engineering paths from reconfiguration history that are inside the current required scope. Introduced-defect and excess-complexity findings bind to those changed paths; outside them, only missing mandatory implementation inside the required scope or a direct regression caused by the candidate on a supported path or deterministic trace is eligible. For a post-Docs `documentation_changes` Review, exact Docs `candidate_changes` are both required scope and complete target. A worker is the sole product mutation owner during its assignment and never runs assigned planned-command argv. Engineering may use exposed computer/editor tools for in-scope persistent edits; QA may use them for temporary gameplay/input/console checks without modifying persistent product files. The shared invariant governs session ownership and cleanup. It stops before returning the artifact. On `complete`, the controller runs the exact planned argv synchronously against the canonical live checkout and compares the Git candidate tree immediately before and after each contained process tree. Any candidate change fails closed before later commands and without a state commit; the controller does not roll bytes back. Ignored temporary, cache, editor, and ordinary log files are outside pipeline control and are neither redirected, classified, nor cleaned. The current runtime defines no controller scratch path.

A Review finding follows the linked role contract: concrete current-candidate evidence, reachable supported game behavior or a deterministic code trace, material violation of mandatory approved behavior/acceptance or concrete target-added excess complexity, and a smallest correction inside the target. That contract also admits a concrete unsupported or unauthorized technical decision governing the target. Theoretical or extremely unlikely risks, unsupported misuse, manual tampering, future-scale concerns, unrequested security hardening, style/nit/refactor preferences, optional cleanup, tests merely for completeness, and pre-existing unrelated issues are excluded. KISS/YAGNI rejects target-added abstraction, state, configuration, fallback, dependency, or lifecycle that authority does not need when a simpler sufficient implementation exists; it never requires additional generality or defensive infrastructure. Review passes with empty findings and stops once mandatory behavior, directly affected integrations, applicable decisions, and minimal sufficient complexity are verified. It returns no suggestions or backlog. Questions are only reversible technical clarifications within consistent authority on a passing result; unresolved product/scope authority choices use `blocked` with the exact user-owned decision. `blocked` also covers a mandatory input or capability still unavailable after the shared assessment. Technical correction uses existing remediation rather than automatic upstream return.

Read-only checks MUST NOT create any full or partial project/candidate copy. Materialized checkouts, clones, snapshots, worktrees, hard-link trees, reflinks, block clones, and copy-on-write checkouts are forbidden. Checks operate only on the canonical live checkout.

Each planned command and all descendants have one controller-owned lifetime. The controller proves containment capability before target code can run, terminates remaining descendants after every normal or timed result, drains output with bounded memory, records timeout return code `124`, and records controller launch or process-tree-control failure with distinct technical return code `125`. Windows uses a kill-on-close Job. Linux requires a successfully probed util-linux PID namespace (`unshare --pid --fork --kill-child=KILL`), trying direct capability before a user namespace mapped to the current user. A controller-owned wrapper installs `PR_SET_PDEATHSIG`; adapter death kills namespace PID 1, after which the kernel kills every namespace member even if it called `setsid` or scrubbed its environment. If this kernel containment is unavailable, or on another POSIX host, the controller returns `125` before launching the target; there is no PID scan, numeric kill, process-group heuristic, or permissive fallback.

Planned commands execute in order only through the first non-zero result. The controller compares the Git candidate tree before and after every executed command, including the failing command, and accepts only a complete all-pass list or the exact prefix ending in its first failure. With no tree drift, a non-zero result preserves the worker artifact unchanged and stores exact argv/return code/full stdout and stderr digests. Only failure evidence additionally stores a redacted and project-path-normalized stderr tail of at most 4096 UTF-8 bytes with explicit truncation/redaction flags; sensitive token/PAT/database-URL/DSN environment values and URI userinfo are redacted, while stdout, environment, cwd, and full stderr are never persisted. Worker or controller failure stores the current candidate only as non-credit artifact evidence. Product Review/QA failure atomically routes to writable Engineering; a failed Review of the controller-issued documentation_changes target routes to the existing Docs owner and exposes only its bound candidate plus deterministic findings/checks and any safe controller-failure capsule; blocker, required action, resolution, argv, and raw process context are never copied. A valid `blocked` artifact is accepted only after artifact, live-tree, CAS, authority, runtime, and replay preflight; it runs no commands, stores `commands: []`, creates no candidate or phase credit, and terminates with its non-empty `blocker`, `required_action`, and `user_input_required=true`. `next` remains forbidden. After the prerequisite changes, the sole continuation is the exact `status`-derived same-run `init`; its action keeps the blocker and required action visible with `user_input_required=true`, so status does not authorize a blind retry. Exact replay is a byte-noop and never reruns checks. Candidate-tree drift, authority or runtime drift, policy-file changes, forbidden changed paths, non-prefix evidence, success truncation, evidence after failure, and malformed excerpts fail closed without state mutation. Schema is `4`; its sole live checkout model is `git-tree-v1`, and older state is rejected without migration.

Workers receive semantic context, not controller bookkeeping. The issued `artifact_schema` is the sole field/type contract; the shared invariant owns preflight and format correction. A minimal passing Plan or unchanged Slice result is:

QA additionally receives the exact `context.required_identity_ids` parsed from the approved current slice's existing Coverage Contract. The plan uses an explicit duplicate-free comma-separated list of `AUTO-...` and `MANUAL-...` IDs; prose derivations or wildcard inventories do not seal. The existing four-field runtime slice format is unchanged. QA writes one structured `{id,outcome,evidence}` result for each mandatory identity; `pass` requires exact set equality and all outcomes `pass`. `complete` rejects invalid coverage before executing planned commands, and `accept`/`ready` revalidate that coverage against the same approved authority. This proves complete bound reporting, not the truth of runtime observations; actual integration evidence remains the QA worker's responsibility.

```json
{"outcome":"pass","summary":"Approved intent and the unchanged slice are confirmed."}
```

Engineering, Review, and QA examples live in their linked role contracts. Changed Slice records still use only the three caller-owned keys described above. Mechanical checkout evidence, process results, replay protection, and atomic state commits are controller-owned and must not appear in a worker artifact.

After authority reconfiguration, the Director executes the exact `init` action with the prior safe slice list and controller-recomputed read binding. Planning revalidates intent, and the Slicer may replace the three caller-owned fields through its semantic artifact only when its ordered IDs match the approved plan; the controller re-derives `read_paths` before reduction. This keeps `status.next_action` exactly executable while leaving product decomposition with the planning role rather than caller-authored CLI bookkeeping.

The controller preserves one latest `candidate_tree_oid` as non-credit artifact evidence whenever semantic credit is invalidated. Initial `init` and authority reconfiguration seal that lock-bound tree in the ordinary non-passing Plan artifact shape. Engineering attempts and changed Docs candidates store exactly `base_tree_oid`, `candidate_tree_oid`, sorted literal `changed_paths`, authority/runtime digests, violations, and command receipts; only a passing worker with all controller commands passing grants candidate credit. An active assignment base contains only its `candidate_tree_oid`. In inactive Engineering, the newest same-authority failed Review/QA binding or non-passing Engineering candidate newer than the last completed-slice boundary is the execution base without becoming phase credit. Reconfiguration generation, authority/runtime binding, accepted-slice history, and questions prevent retained evidence from advancing a phase. Retained Engineering paths remain Review targets within the current slice even when the fresh Engineering diff is empty; sealing a new execution baseline never grants those edits Review credit. The status-derived reconfiguration command ID binds the observed tree OID. `status` and every mutation or exact replay validate the live candidate tree against the current epoch baseline under the state lock. Schema-2 state fails closed with fresh-`init` guidance; there is no dual reader, migration, or fallback.

## Rework and readiness

After a product Review or QA `fail`, `complete` preserves the failing artifact and candidate binding, invalidates engineering and downstream credit, and selects writable Engineering. A Review failure on the issued `documentation_changes` target instead selects the existing Docs owner with its approved documentation scope; the repaired or reverted Docs target must receive fresh Review and QA. QA tests product acceptance and planned commands, so its failure remains an Engineering repair even after Docs. The already reviewed Docs tree is then the Engineering execution baseline; retained documentation changes are not attributed to the new product delta. Reverification of the final slice does not append a duplicate completed-slice marker. The next assignment receives only the deterministic failing findings/checks and safe controller-failure capsule bound to that candidate. The repaired candidate must pass fresh Review and QA. A `blocked` outcome cannot be resumed or advanced in place; only the exact public same-run `status` → `init` recovery is available after its external prerequisite changes. A documentation change also routes through fresh Review and QA.

Schema-10 import and reconstruction do not execute. The retained `migrate` surface always returns the stable unsupported/fresh-init error and never writes controller state.

The runtime is replay-safe and compare-and-swap protected. Exact repeated commands are no-ops only while authority and the retained live-checkout baseline still match; `next` checks its recorded-generation intent before current-generation assignment defaults, preserving exact omitted-identity and explicit-identity lost-response replays. Conflicting, stale, or drifted writes fail without mutation. State replacement is atomic, and native process locks are released after a crash.

`ready` additionally requires a completed-slice prefix equal to the entire approved ordered slice list. It means production-ready candidate only; it does not authorize deployment, publication, spending, submission, or risk acceptance.
