# Pipeline v2 protocol

Read only the named section for the current operation. The shared lifecycle, authority and delivery contracts own their respective policies; this file describes runtime boundaries and legacy-compatible recovery forms. New active checks and targeted recovery are in [execution and recovery](execution-contract.md).

## Authority and phases

Apply the shared [technical decisions](technical-decisions.md) policy. Approved source files remain immutable within an authority epoch. Their exact paths and planned checks seal the base contract; a controller-admitted active-Engineering technical decision may add exact incidental file paths or reorder the same planned argv without changing product authority or acceptance. In assignment rules below, current slice access and command order mean that controller-derived effective execution contract. Initialization and upstream source equality still use the unchanged approved base. Neither free-form journal text nor caller-authored assignment changes grant an overlay.

Approved requirements, specification, and development plan files are immutable authority for an authority epoch. `init` accepts exactly the authority keys `requirements`, `specification`, and `plan`, one compact safe ASCII run identifier, and at least one caller slice record with exactly `id`, `allowed_paths`, and `planned_commands`. For initial `init`, the Director mechanically copies exact approved/native/setup slice fields and already serialized `planned_commands` argv. If the approved plan supplies only prose methods, the existing authorized responsible specialist supplies bounded method-to-argv serialization using observed repository tools; the Director forwards that question/result without semantic selection. No new Planning artifact or repeated approval is required merely for serialization. Preserve approved methods, scope and mandatory checks; substantive changes retain their actual authority route. Missing tools/prerequisites are separate facts, not waived checks. For each slice, the controller parses the approved plan's ordered `Owned Paths`, requires it to exactly equal ordered `Scope Contract.editable_paths`, and requires caller `allowed_paths` to be byte/order-identical; narrowing, broadening, duplicates, invalid paths, and reordering fail closed. The controller separately derives and stores the fourth `read_paths` field from Context Capsule `authority_paths` plus `evidence_paths`; IDs must match exactly, paths are deduplicated canonical project-relative exact or terminal `dir/**` rules, every disjoint `Expected Paths` entry must be covered, and caller-authored read scope is rejected. `allowed_paths` remains the sole write authority; no specification semantics are inferred. The run ID starts and ends alphanumeric, is at most 64 characters, and otherwise permits only dots, underscores, or hyphens. The same command can rebind changed approved authority or an old three-key live scope under generation CAS, restart planning, and retain the prior candidate/history as audit context. Sole runtime v2 has no `authority_recovery_hold`: a sanctioned upstream controller may reopen its own authority, after which `status` observes authority and checkout under the state lock and returns one exact `init` whose command ID binds the observed authority paths/bytes and controller-projected four-key slices. Execution recomputes and validates that binding under the lock; every other public mutation fails closed, and every replay fails closed, on drift or an old unsealed scope without a state write. Execute that `init` only after every changed upstream controller reports readiness for the exact current bytes; unsanctioned drift must be restored or reconciled upstream first. An active assignment may be interrupted only after the controller proves its checkout diff stays within the old assignment; pre-existing foreign drift yields the non-mutating terminal status `checkout_recovery_required` instead of an unusable `init`, and retained product Engineering paths from blocked candidates and active interruptions must remain covered. Historical workflow evidence is provenance/read context, not a demand to widen product write scope. Separately authorized runtime maintenance can rebind an idle run through the same explicit `status` → `init` route: the command ID additionally binds the observed runtime digest, the checkout and history are retained, and stale phase credit is cleared. Runtime changes with an active assignment require the explicit maintenance route below; every normal mutation on a stale runtime remains forbidden. Authority path comparisons follow host filesystem case semantics, so spelling aliases never turn sanctioned authority drift into foreign checkout drift. Never edit controller state directly.

A genuine suspected controller invariant/runtime defect pauses affected product transitions. Classify public errors first; malformed artifacts, stale actions, reproduced product defects and unavailable capabilities have their own routes. Do not patch or bypass the pipeline under product-only authority. Separate maintenance requires applicable explicit authority under [authority contract](authority-contract.md), including valid prior delegation; do not demand a new approval already supplied for this exact scope.

The seven phases are `plan`, `slice`, `engineering`, `review`, `qa`, `docs`, and `ready`. The controller derives every transition. Each ordered slice passes Engineering, independent current-candidate Review and QA before the next slice; documentation starts after the final slice. If the exact approved plan and every slice explicitly declare derived post-QA documentation `not_required`, and all normative pre-Review paths are existing literal Engineering-owned files in the accepted Git candidate (or explicitly `not_required`), final QA acceptance goes directly to the guarded `ready` action, recording `documentation_not_required` without a Docs assignment, worker or artifact. Missing/malformed declarations and required documentation retain the Docs route. A passing phase is committed with `complete` and advanced with `accept`; a question returns to the phase that produced it, while `blocked` terminates the phase with `user_input_required=true`. It cannot be blindly retried. After the prerequisite changes, guarded `recover-capability` may preserve proven unchanged prefix/credit; other cases use the exact bound public recovery action under the [shared stage-handoff invariant](stage-handoff-invariant.md). Unchanged blocked status exposes the bound `recover-capability` evidence route; ordinary `init` is rejected for that unchanged boundary. Existing same-run `init` remains available for its specific changed-authority, changed-runtime or explicitly authorized baseline/recovery contract, preserving terminal history without treating a resolved capability as a new plan. Documentation changes must pass a fresh Review and QA before `ready`.

An explicitly authorized prerequisite baseline can be adopted by existing `init` after the first genuine Engineering `blocked` result, before product work. Admission requires no active assignment, one initial epoch and exactly one completed Engineering attempt, only Plan/Slice/Engineering records whose controller base/candidate trees equal the initial baseline, empty changed paths/violations and no controller failure. Current approved authority passes its source-chain validator, including any sanctioned fully reconverged revision; repository policy stays unchanged; the proposed candidate must be a clean committed Git tree. Both `status` and `init` enforce this boundary. The existing action binds the fresh tree, generation, authority, slices and runtime; same-tree HEAD metadata is not a separate identity. A commit alone is not user authorization. Successful init preserves the old candidate and terminal history as audit context, records the new non-credit baseline and restarts Plan. Dirty state, later/reconfigured runs, active work and retained product changes do not gain this exception; their existing fail-closed behavior remains.

## Newly evidenced product failure after terminal QA

When new read-only observation establishes a product defect on the unchanged terminal blocked QA candidate, explicit user authorization may route it directly to ordinary Engineering remediation. This is not a retry of the blocked scenario or a QA waiver. Run `status --product-failure`. The Director mechanically copies `product_failure_binding` once into a retained exact workflow-local JSON path and adds only actual sourced `authorization`; the existing authorized QA specialist supplies unchanged `evidence_path`, `evidence_sha256`, and `checks`. Obtain missing QA input through one correlated caller task and consume its `task_result` before assembly. No native assignment is fabricated for that idle evidence task. The binding contains `run_id`, `feature`, `generation`, `qa_assignment_id`, `candidate_tree_oid`, `authority_digest`, `slice_digest`, and `runtime_digest`. Evidence must be a nonempty workflow-local file with the exact SHA256; checks must be nonempty existing QA identities, each `{id, outcome: "fail", evidence}` describing only the new observation and its source. No passing checks or claimed previous execution may be invented. Then run `status --product-failure <packet>` and its exact `init --product-failure <same-packet>`. Candidate, authority, scope and evidence are rechecked; other recovery packets cannot be combined.

This narrow init preserves the complete original blocked artifact separately in `history[].prior_artifacts`, records the authorized observation packet, invalidates Engineering and downstream credit, and selects Engineering on the same candidate tree and scope. Only the noncredit failure binding is rebound to the maintained runtime; original evidence remains unchanged in history. New current-candidate Engineering, Review and QA assessments are still mandatory, and no readiness or successful QA credit is granted. Without newly bound evidence, ordinary terminal behavior remains unchanged.

## Active assignment maintenance

A separately authorized controller repair can retire an active Engineering assignment only after the Director has stopped its worker and all owned activity. This does not permit maintenance during ordinary product work. First run `status --maintenance` after the repaired runtime is stable. This read-only observation returns `maintenance_binding` and no executable mutation. The Director copies that binding once into a retained exact workflow-local JSON path and adds exactly two non-empty text fields: `authorization`, identifying the actual user permission for this separate maintenance, and `quiescence`, identifying how the Director stopped the worker and established that no owned activity remains. These are factual Director attestations, not consent inferred from silence or a machine guarantee against an undisclosed concurrent writer.

The binding contains exactly `run_id`, `feature`, `generation`, `assignment_id`, `candidate_tree_oid`, `authority_digest`, `slice_digest`, `previous_runtime_digest`, and `runtime_digest`. Run `status --maintenance <file>` and execute its exact `init` with `--maintenance <same-file>`. The active candidate may retain changes proven within the old Engineering scope after factual quiescence; unrelated or out-of-scope drift is rejected. Its terminal output file must not exist; the packet must bind the exact observed tree, and approved authority, slice scope and repository policy must be unchanged. Runtime bytes must have changed. A missing/stale packet, candidate change after its binding, out-of-scope drift, terminal output, authority/policy/assignment/generation mismatch or runtime-binding mismatch fails closed. This cannot be combined with checkout recovery. Ordinary status/next/complete and an unqualified init do not bypass the active-runtime guard.

Init archives the interrupted assignment, original candidate and context, complete failed Review/QA artifact and deterministic failure evidence, preserving every finding/check. It clears live credit and restarts Plan; the former worker and assignment must not be resumed. After fresh Plan and Slice, Engineering receives the existing `verification_failure` shape as full historical correction evidence only while the exact candidate tree, authority and slice still match. Its original source candidate remains unchanged and grants no phase credit; the new capsule has no credited candidate. Current-candidate Engineering, independent Review and QA remain mandatory, and retained changed paths stay in the Review target. Exact lost-response replay changes no state while its original packet, candidate, runtime, authority and absent output still match.

Public active-assignment views preserve complete issued obligations and restore legacy clipped content only from matching canonical evidence. Required findings, checks, technical decisions and operative answered questions are never shortened or omitted. The existing Review-target fallback still applies. This preserves the deterministic failure binding, findings/checks and all other issued context through status and next replay.

## Authorized checkout recovery

This section describes only the legacy `status --recovery` / `init --recovery` pair. Its blocked-Engineering eligibility and packet `kind` fields do not apply to the newer idle `reconcile` action. For an authorized external change after an accepted slice, use [Choose the narrow recovery](execution-contract.md#choose-the-narrow-recovery), including its distinct exact packet, before considering the legacy pair.

After the user explicitly authorizes resolving a blocked Engineering prerequisite, the Director may supply a JSON file through `status --recovery <path>` and the returned exact `init --recovery <same-path>`. Store it in the selected workflow directory, outside product candidate evidence. This is the existing conservative same-run reconfiguration; guarded `reconcile` covers additional idle external-change cases and `recover-capability` covers unchanged-input prerequisite recovery. Neither is a blind in-place retry. The unqualified status/init path retains its existing refusals.

Start with `next_action.recovery_binding` from fresh status. Copy its `run_id`, `feature`, `generation`, `base_tree_oid`, `candidate_tree_oid`, and `authority_digest` exactly. Replace `changed_paths` with an ordered `paths` array containing exactly those paths. Each entry has exactly `path`, `kind`, `authorization`, and `provenance`. `kind` is `retained_engineering` for paths in the current approved Engineering scope, otherwise `external_prerequisite`. The Director supplies actual sourced per-path `authorization`; the existing responsible authorized specialist supplies exact `provenance` of origin/resolved prerequisite and the required classification facts. The Director assembles the native field list once at a retained exact workflow-local path, preserving native path order and supplied facts. A missing specialist input uses one correlated caller task before assembly. These attestations are not machine proof of consent or cause; never fabricate or infer them from a diff or commit. Missing or uncertain provenance requires resolving the ownership question before this action. Do not classify out-of-scope product implementation as an external prerequisite.

Only an inactive, genuine blocked Engineering artifact with valid controller evidence and no controller failure or scope violation qualifies. Approved authority must remain byte-identical and its complete source chain must validate. Repository policy (`.gitignore`, `.gitattributes`, `.gitmodules`) cannot change. Every observed drift path needs exactly one authorization; stale generation, run, feature, baseline, candidate, authority, missing/extra paths, classification and provenance are rejected without state mutation. No commit is required. Read fresh packet-bearing status, then execute its exact action with that same packet. The action also binds the current runtime digest. Packet edits or checkout changes invalidate it.

Successful init archives the packet with the prior candidate and terminal history, keeps the current journal, clears phase credit and restarts Plan. Existing retained Engineering paths and restored in-scope paths must remain covered by the new Slicer and Review, even when Engineering subsequently leaves their bytes unchanged. External prerequisite paths are recorded for audit, not accepted as Engineering work or phase credit. Exact lost-response replay is a state-byte no-op only while the bound checkout, authority, runtime and original packet still match. This route does not grant workers new write scope, weaken Review/QA or authorize publication.

## Commands

For bounded assignment export, source pagination, same-worker delivery updates and one-step mechanical execution, use the [delivery contract](delivery-contract.md). These interfaces reuse the same runtime, authority and action bindings; they do not add phases or permission routes.

- `init`: create a v2 run, or reconfigure changed approved authority/scope/runtime at a safe boundary.
- `status`: read the current public view and its one controller-derived `next_action` without mutation. Directors request global `--brief` before this subcommand to keep assignment content out of routine observations; the full compatible public view remains available for explicit reads.
- `next`: issue one bounded assignment for the current phase, deriving its canonical identity, task, access, checks, and Review target from controller state; compatibility identity flags may be omitted and must match exactly when supplied.
- `complete`: consume one semantic worker artifact; fail/blocked runs no granting suite. Passing work requires controller-valid current evidence, including permitted deterministic receipt reuse.
- `answer`: record the exact safest reversible authority-consistent answer selected by the existing responsible authorized specialist and transmitted by Director; invalidate the affected artifact. Missing semantic authority remains a user decision, not implicit delegation.
- `accept`: advance from the current passing artifact.
- `migrate`: retained fail-closed tombstone; schema-10 migration is unsupported by `git-tree-v1`, so archive legacy state/findings and run fresh Plan/`init`.
- `ready`: seal the live, independently reviewed and tested terminal candidate.
- `technical-observe`: capture a clean scoped before-action checkout observation for the active Engineer.
- `technical-decision`: bind a current technical decision and bounded execution adjustment to that same active assignment and observed checkout.

Additional public routes use the exact contracts in [execution and recovery](execution-contract.md):

- `check`: diagnostic planned checks while Engineering or read-only QA is active and quiescent, without phase PASS or manual acceptance.
- `rotate-owner`: retire the idle current role alias after a factual checkpoint/turnover.
- `read-admit`: exact in-project read-only dependency admission, never write/review-scope authority.
- `recover-capability`: resume the blocked phase after evidenced prerequisite change with unchanged bindings.
- `reconcile`: admit exactly enumerated authorized external changes and invalidate affected evidence.
- `pin-runtime`: create a new immutable verified bundle copy for the run's launcher.

Exact flags belong to each command's `--help`; do not copy old command recipes into worker prompts.

## Technical action interface

Only active Engineering may request these two actions; the Director executes them while the same Engineer remains the sole product writer. Read fresh `status.technical_actions` for the expected generation and observed tree, including when ordinary `next_action` reports checkout recovery. Use `technical-observe --id <command-id> --expected-generation <generation> --action <description>` before an editor/tool action that can produce persistent incidental changes. A valid scoped tree is required. The resulting `active_assignment.technical_observation` binds its ID, tree, action, and assignment; an observation made after foreign drift cannot establish its origin.

The Engineer may write the bounded request only to `.agentic-pipeline/Workflows/<feature>/technical-decision-request.json`, separate from candidate files and its terminal semantic artifact. The Director submits it with `technical-decision --id <command-id> --expected-generation <generation> --packet <request-path>`. Required packet fields are `assignment_id`, the fresh `observed_tree_oid`, and `entry` in the shared journal shape. Optional `additional_paths` lists exact files, never broad patterns; `command_order` is a non-empty permutation of the unchanged planned argv list; `observation_id` binds reconciliation to the earlier controller observation. Omitted adjustment fields retain this entry's existing adjustment. Explicit empty `additional_paths` removes it only if remaining governed scope still covers actual changes; explicit empty `command_order` is invalid. The caller creates a unique command ID for these two explicit actions; assignment, tree and observation identities come from current controller evidence, never narrative guesses.

For unexpected checkout changes, first establish their cause and effect. Reconciliation admits exactly the foreign paths arising after the saved observation and covered by the requested exact-file adjustment; pre-existing foreign drift and known unrelated/user changes remain excluded. The observation and sole-writer discipline support provenance but do not prove that an unrelated concurrent writer did not act. If provenance is unresolved, use the existing recovery route. A file type or normal editor behavior alone is insufficient evidence.

After success, use the returned fresh binding and send current export/delta to the same physical Engineer before further mutation. Read status only when that binding is missing/stale or an external change is evidenced. The Engineer consumes changed identity/output, journal, access and command order; the Director forwards transport rather than selecting journal semantics. An ordinary technical operation reorder inside existing access does not require a controller action; include its decision in the terminal semantic artifact. A public technical action never weakens tests, admits product choices, changes approved technology, edits authority, or grants ready credit.

Every runtime role may submit current `technical_decisions` entries through its issued artifact. They replace the same ID in the feature-local current journal and cannot supply sealed execution fields. Existing execution adjustments remain controller-owned. Review/QA corrections requiring changed implementation or execution use ordinary `fail` remediation; a passing entry describes the candidate actually assessed. Semantic journal changes require freshness checks and renewed affected phase verification before acceptance, never credit based on an older record. Explicit diagnostic-only `observations` do not alter semantic evidence; counterevidence must update the affected semantic decision/basis/checks and invalidate dependent credit. `init` and reconfiguration preserve the current journal. Reentered upstream stages consume it through their shared read-only interface; a user-approved local authority amendment uses the owning stage's targeted revision/approval and ordinary runtime reconfiguration, without requiring full document regeneration unless needed or requested.

Mutating `init` validates the approved PRD, the specification's exact PRD trace, and the plan's exact PRD/specification traces using the existing Planning parsers. It reads no additional stage-state registry. `status` remains read-only and exposes recovery while upstream documents are being reconverged.

The Director executes `status.next_action` for ordinary lifecycle work and the bounded `technical_actions` interface for an active Engineering request; it does not invent generations, assignment identities, output paths, access rules, checks, Review targets, question IDs, or recovery reasons. The sole worker-invoked workflow mutation is an explicitly granted active Engineering/QA `check` under the [execution contract](execution-contract.md#check-inside-active-engineering-or-qa); that cooperative grant adds no other command, lifecycle, recovery, journal, direct-argv, or state-edit authority. Every invocation supplies exact `--root` and lowercase `--feature`; the controller derives `.agentic-pipeline/Workflows/<feature>/pipeline-state.json`, rejects foreign/escaping/linked bindings before mutation, and never scans or changes a sibling workflow. `controller_decision` actions include a conservative authority-consistent policy. The existing responsible authorized specialist selects the exact answer; the Director forwards it with the current question/CAS binding. Product choices and exclusive approval acts remain with their actual authorized actor; no silent redelegation or approval of unseen content.

## Assignment and artifact boundaries

Runtime Plan/Slice and other production workers receiving `control_binding` first apply the shared [control-return contract](control-return.md) outside their unchanged semantic artifact. Return native assignment events with issued IDs; a separate caller task returns `task_result` without invented runtime IDs. The wrapper does not start another stage or grant product writes.

Only one assignment may be active. It exposes a controller-derived `artifact_schema` and one controller-derived `output_path` under `.agentic-pipeline/Workflows/<feature>/outputs/`; the worker follows that schema without reading runtime code, writes its semantic JSON only there, and `complete` reads only that exact path. Controller and history paths may remain Git-tracked; tracked and untracked control paths are excluded before live worktree staging can open them and remain absent from candidate evidence, while non-control authority, product, and repository-policy drift remains governed, so semantic output cannot create candidate drift. Every staged or policy path passes the same effective candidate classifier: tracked and non-ignored non-control policies remain governed, an ignored policy remains governed only while its parent is Git-traversable and it can hide otherwise candidate-visible paths, and policy inside an already ignored subtree stays outside with the other ignored editor or cache bytes. Every newly issued assignment uses a worker ID absent from controller-owned completed actor history, and Engineer IDs cannot be reused for Review or QA. A rejected output format with the same active assignment uses the shared same-worker artifact correction rule; it is not a new assignment. The controller derives canonical read/write access, checks, and Review target again for every `next`; omitted or conflicting caller values never change the issued packet. Planning, slicing, Review, and QA receive no candidate write access. Engineering scope and checks come from the current slice. Documentation receives controller-derived project-relative write paths. Authority files are never writable.

Workers run only the scenarios supplied by the assignment. Engineering, Review, and QA read access is the deterministic deduplicated union of authority plus every completed/current slice's `allowed_paths` and sealed `read_paths`; a post-Docs Review also reads its exact changed Docs target paths. Engineering write access and Engineering/QA checks remain exactly the current slice's `allowed_paths` and `planned_commands`, and future slices remain unreadable. Review read access outside the target is evidence context, not audit scope. For `current_slice_implementation`, the small controller-derived `context.review_target.required_scope` equals `current_slice.allowed_paths`, while `candidate_changes` lists accepted Engineering controller changed paths plus retained Engineering paths from reconfiguration history that are inside the current required scope. Introduced-defect and excess-complexity findings bind to those changed paths; outside them, only missing mandatory implementation inside the required scope or a direct regression caused by the candidate on a supported path or deterministic trace is eligible. For a post-Docs `documentation_changes` Review, exact Docs `candidate_changes` are both required scope and complete target. A worker is the sole product mutation owner during its assignment and never runs assigned planned-command argv. Engineering may use exposed computer/editor tools for in-scope persistent edits; QA may use them for temporary gameplay/input/console checks without modifying persistent product files. The shared invariant governs session ownership and cleanup. It stops before returning the artifact. On active Engineering `check` or passing `complete`, the controller runs required exact planned argv or validates eligible deterministic receipts against the canonical live checkout and compares the Git candidate tree immediately before and after each contained process tree. Any candidate change fails closed before later commands and without a state commit; the controller does not roll bytes back. Ignored temporary, cache, editor, and ordinary log files are outside pipeline control and are neither redirected, classified, nor cleaned. The current runtime defines no controller scratch path.

Review eligibility, scope and finding IDs follow the [Review artifact contract](../../gamedev-review/references/review-output-contract.md). Additional read access is evidence context, not additional audit scope. Rework targets open findings, the changed diff and affected integrations, with fresh evidence and no optional improvement hunt.

Read-only checks MUST NOT create any full or partial project/candidate copy. Materialized checkouts, clones, snapshots, worktrees, hard-link trees, reflinks, block clones, and copy-on-write checkouts are forbidden. Checks operate only on the canonical live checkout.

Each planned command and all descendants have one controller-owned lifetime. The controller proves containment capability before target code can run, terminates remaining descendants after every normal or timed result, drains output with bounded memory, records timeout return code `124`, and records controller launch or process-tree-control failure with distinct technical return code `125`. Windows uses a kill-on-close Job. Linux requires a successfully probed util-linux PID namespace (`unshare --pid --fork --kill-child=KILL`), trying direct capability before a user namespace mapped to the current user. A controller-owned wrapper installs `PR_SET_PDEATHSIG`; adapter death kills namespace PID 1, after which the kernel kills every namespace member even if it called `setsid` or scrubbed its environment. If this kernel containment is unavailable, or on another POSIX host, the controller returns `125` before launching the target; there is no PID scan, numeric kill, process-group heuristic, or permissive fallback.

Granting checks execute in dependency order and stop credit at failure. Active diagnostic `check --collect-independent` may additionally collect recipe-declared independent failures while prerequisites and candidate containment remain valid. The controller compares the Git candidate tree before and after every executed command, including the failing command, and accepts credit only for a complete valid all-pass set; diagnostic receipts remain non-credit and retain every actually executed result. With no tree drift, a non-zero result preserves the worker artifact unchanged and stores exact argv/return code/full stdout and stderr digests. Failure evidence additionally stores bounded redacted stdout/stderr tails with truncation flags, stream digests and exact command/check binding. Sensitive token/PAT/database-URL/DSN values and URI userinfo are redacted; full streams and environment are not copied into worker context. Receipts report duration and whether execution was fresh or reused, with its reason/source receipt. Worker or controller failure stores the current candidate only as non-credit artifact evidence. Product Review/QA failure atomically routes to writable Engineering; a failed Review of the controller-issued documentation_changes target routes to the existing Docs owner and exposes only its bound candidate plus deterministic findings/checks and any safe controller-failure capsule; blocker, required action, resolution, argv, and raw process context are never copied. A valid semantic fail/blocked artifact is consumed only after artifact, live-tree, CAS, authority, runtime and replay preflight; it runs no granting commands, stores `commands: []`, creates no candidate or phase credit, and terminates with its non-empty `blocker`, `required_action`, and `user_input_required=true`. `next` remains forbidden. After the prerequisite changes, use the exact bound `recover-capability` evidence route where its unchanged-input contract holds; status keeps the blocker and required action visible with `user_input_required=true`, so it authorizes no blind retry. Changed authority/runtime/baseline and explicit product-failure recovery retain only their existing bound routes; ordinary unchanged `init` cannot replace narrow recovery. Exact replay is a byte-noop and never reruns checks. Candidate-tree drift, authority or runtime drift, policy-file changes, forbidden changed paths, invalid granting evidence, success truncation, unsafe diagnostic continuation and malformed excerpts fail closed without state mutation. Schema is `4`; its sole live checkout model is `git-tree-v1`, and older state is rejected without migration.

## Rework and readiness

After a product Review or QA `fail`, `complete` preserves the failing artifact and candidate binding, invalidates engineering and downstream credit, and selects writable Engineering. A Review failure on the issued `documentation_changes` target instead selects the existing Docs owner with its approved documentation scope; the repaired or reverted Docs target must receive fresh Review and QA. QA tests product acceptance and planned commands, so its failure remains an Engineering repair even after Docs. The already reviewed Docs tree is then the Engineering execution baseline; retained documentation changes are not attributed to the new product delta. Reverification of the final slice does not append a duplicate completed-slice marker. The next assignment receives all operative findings/checks, convergence IDs and the bound safe controller-failure capsule, including Engineering gate failures. Its Engineer alias remains stable for remediation. The repaired candidate must pass independent current-candidate Review and QA; independent role owners may retain their applicable context without inheriting previous PASS. A `blocked` outcome cannot be advanced on unchanged evidence. Once its prerequisite changes, `recover-capability` applies only with its unchanged-binding proof; other cases use the exact public recovery route. Documentation changes retain bounded source-fidelity Review; the controller may reuse deterministic product receipts only for sealed pure-documentation paths with unchanged product dependencies.

Schema-10 import and reconstruction do not execute. The retained `migrate` surface always returns the stable unsupported/fresh-init error and never writes controller state.

The runtime is replay-safe and compare-and-swap protected. Exact repeated commands are no-ops only while authority and the retained live-checkout baseline still match; `next` checks its recorded-generation intent before current-generation assignment defaults, preserving exact omitted-identity and explicit-identity lost-response replays. Conflicting, stale, or drifted writes fail without mutation. State replacement is atomic, and native process locks are released after a crash.

`ready` additionally requires a completed-slice prefix equal to the entire approved ordered slice list. It means production-ready candidate only; it does not authorize deployment, publication, spending, submission, or risk acceptance.
