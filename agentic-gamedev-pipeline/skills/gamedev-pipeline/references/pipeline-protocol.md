# Pipeline v2 protocol

This is the complete Director protocol for the sole runtime engine.

## Authority and phases

Approved requirements, specification, and development plan files are immutable authority for an authority epoch. `init` accepts exactly the authority keys `requirements`, `specification`, and `plan`, one compact safe ASCII run identifier, and at least one caller slice record with exactly `id`, `allowed_paths`, and `planned_commands`. The controller alone derives and stores each slice's fourth `read_paths` field from that approved plan slice's Context Capsule `authority_paths` plus `evidence_paths`; IDs must match exactly, paths are deduplicated canonical project-relative exact or terminal `dir/**` rules, and caller-authored read scope is rejected. `allowed_paths` remains the sole write authority. The run ID starts and ends alphanumeric, is at most 64 characters, and otherwise permits only dots, underscores, or hyphens. The same command can rebind changed approved authority or an old three-key live scope under generation CAS, restart planning, and retain the prior candidate/history as audit context. Sole runtime v2 has no `authority_recovery_hold`: a sanctioned upstream controller may reopen its own authority, after which `status` observes authority and checkout under the state lock and returns one exact `init` whose command ID binds the observed authority paths/bytes and controller-projected four-key slices. Execution recomputes and validates that binding under the lock; every other public mutation fails closed, and every replay fails closed, on drift or an old unsealed scope without a state write. Execute that `init` only after every changed upstream controller reports readiness for the exact current bytes; unsanctioned drift must be restored or reconciled upstream first. An active assignment may be interrupted only after the controller proves its checkout diff stays within the old assignment; pre-existing foreign drift yields the non-mutating terminal status `checkout_recovery_required` instead of an unusable `init`, and the fresh Slicer scope must cover interrupted Engineering paths. Authority path comparisons follow host filesystem case semantics, so spelling aliases never turn sanctioned authority drift into foreign checkout drift. Never edit controller state directly.

The seven phases are `plan`, `slice`, `engineering`, `review`, `qa`, `docs`, and `ready`. The controller derives every transition. Each ordered slice passes Engineering, fresh Review, and fresh QA before the next slice; documentation starts after the final slice. A passing phase is committed with `complete` and advanced with `accept`; a question or blocked outcome returns to the phase that produced it. Documentation changes must pass a fresh Review and QA before `ready`.

## Nine commands

- `init`: create a v2 run, or reconfigure changed approved authority/scope at a safe boundary.
- `status`: read the compact current view and its one controller-derived `next_action` without mutation.
- `next`: issue one bounded assignment for the current phase, deriving its canonical identity, task, access, and checks from controller state; compatibility identity flags may be omitted and must match exactly when supplied.
- `complete`: submit one semantic worker artifact; controller evidence is gathered independently.
- `answer`: record the Director's safest reversible authority-consistent assumption and invalidate the affected artifact.
- `resume`: resolve a gate; Review/QA failure routes to engineering remediation, while an external block returns to its source phase.
- `accept`: advance from the current passing artifact.
- `migrate`: import schema-10 audit context and fresh v2 slices once into an empty state, canonicalizing the physical project root and validating the derived run ID. It normally restarts at `plan`; the exact safe first-slice Engineering hold described below preserves Plan/Slice credit and resumes with a fresh v2 Engineer. Both routes seal the observed live checkout for status, mutation, and replay preflight.
- `ready`: seal the live, independently reviewed and tested terminal candidate.

Exact flags belong to each command's `--help`; do not copy old command recipes into worker prompts.

The Director executes `status.next_action`; it does not invent command IDs, generations, assignment identities, output paths, access rules, checks, gate/question IDs, or recovery reasons. The optional controller state path must resolve to one direct `.json` child of the exact project root's `.agentic-pipeline-v2` directory; an external, nested, symlinked, or reparse-point path fails before mutation. `controller_decision` actions include a policy for choosing a conservative product assumption without technical user input.

## Assignment and artifact boundaries

Only one assignment may be active. It exposes a controller-derived `artifact_schema` and one controller-derived `output_path` under `.agentic-pipeline/outputs/`; the worker follows that schema without reading runtime code, writes its semantic JSON only there, and `complete` reads only that exact path. The output area is excluded from checkout inventory, so read-only Planning, slicing, Review, and QA can report without creating candidate drift. Every retry uses a worker ID absent from controller-owned completed actor history, and Engineer IDs cannot be reused for Review or QA. The controller derives canonical read/write access and checks again for every `next`; omitted or conflicting caller values never change the issued packet. Planning, slicing, Review, and QA receive no candidate write access. Engineering scope and checks come from the current slice. Documentation receives controller-derived project-relative write paths. Authority files are never writable.

Workers run only the scenarios supplied by the assignment. Engineering, Review, and QA read access is the deterministic deduplicated union of authority plus every completed/current slice's `allowed_paths` and sealed `read_paths`, while Engineering write access and Engineering/QA checks remain exactly the current slice's `allowed_paths` and `planned_commands`; future slices remain unreadable. A read-only worker never runs or reruns the assigned planned-command argv itself. On `complete`, the controller runs that exact argv against the canonical live checkout. Every read-only planned command MUST be non-mutating: temporary and cache data is redirected to bounded controller-owned scratch under excluded `.agentic-pipeline-v2/read-only-temp/`, and that scratch contains no copied candidate content and is cleaned after the process tree ends. Immediately after each planned process tree ends, the controller inventories and diffs the candidate against the assignment base before it may start the next command. Detected drift fails closed before later commands and without a controller state commit. The controller does not roll candidate bytes back, so a forbidden live mutation remains dirty and requires recovery.

Read-only checks MUST NOT create any full or partial project/candidate copy. Materialized checkouts, clones, snapshots, worktrees, hard-link trees, reflinks, block clones, and copy-on-write checkouts are forbidden. Checks operate only on the canonical live checkout; scratch is control data, never a second project tree.

Each planned command and all descendants have one controller-owned lifetime. The controller proves containment capability before target code can run, terminates remaining descendants after every normal or timed result, drains output with bounded memory, records timeout return code `124`, records controller launch or process-tree-control failure with the distinct technical return code `125`, and retries read-only scratch cleanup for a bounded interval before failing closed. Windows cleanup changes permissions and retries only the exact failed lexical path inside the already verified scratch root; it does not prewalk or follow a symlink/junction/reparse target. Windows uses a kill-on-close Job. Linux requires a successfully probed util-linux PID namespace (`unshare --pid --fork --kill-child=KILL`), trying direct capability before a user namespace mapped to the current user. A controller-owned wrapper installs `PR_SET_PDEATHSIG`; adapter death kills namespace PID 1, after which the kernel kills every namespace member even if it called `setsid` or scrubbed its environment. If this kernel containment is unavailable, or on another POSIX host, the controller returns `125` before launching the target; there is no PID scan, numeric kill, process-group heuristic, or permissive fallback.

Planned commands execute in order only through the first non-zero result. The controller inventories and checks drift after every executed command, including the failing command, and accepts only a complete all-pass list or the exact prefix ending in its first failure. With no drift, a non-zero result preserves the worker artifact unchanged and stores exact argv/return code/full stdout and stderr digests. Only failure evidence additionally stores a redacted and project/scratch-normalized stderr tail of at most 4096 UTF-8 bytes with explicit truncation/redaction flags; sensitive token/PAT/database-URL/DSN environment values and URI userinfo are redacted, while stdout, environment, cwd, and full stderr are never persisted. Worker `fail`/`blocked` keeps the ordinary worker-result gate and attaches the same safe controller-failure capsule when a controller check also fails. Worker `pass` plus controller failure instead atomically closes the assignment, opens a distinct controller-result gate, grants no candidate or phase credit, and exposes `resume`; QA controller failure resumes in writable Engineering. Public `complete`/`status` expose only the safe failure capsule under `next_action.gate.controller_failure` (one-based command index, return code, stdout/stderr digests, bounded excerpt and flags, and unexecuted-command count), and the same capsule is retained in the fresh remediation assignment context without argv or raw process context. Exact replay is a byte-noop and never reruns checks. Checkout drift, authority drift, forbidden checkout changes, non-prefix evidence, success truncation, evidence after failure, and malformed excerpts fail closed without state mutation. Schema remains `2`, and legacy four-field failure command evidence remains valid.

Workers receive semantic context, not controller bookkeeping. Accepted worker artifacts are deliberately small:

```text
plan:         outcome, non-empty summary, optional questions
slice:        outcome, summary, optional ordered slices and questions
engineering: outcome, summary, optional assumptions and questions
review:      outcome, findings[{text,severity,kind}], optional questions
qa:          outcome, checks, blocker when blocked, optional questions
docs:        outcome, summary, optional questions
```

`outcome` is `pass`, `fail`, or `blocked`. Questions are concise strings. Mechanical checkout evidence, process results, replay protection, and atomic state commits are controller-owned and must not appear in a worker artifact.

After authority reconfiguration, the Director executes the exact `init` action with the prior safe slice list and controller-recomputed read binding. Planning revalidates intent, and the Slicer may replace the three caller-owned fields through its semantic artifact only when its ordered IDs match the approved plan; the controller re-derives `read_paths` before reduction. This keeps `status.next_action` exactly executable while leaving product decomposition with the planning role rather than caller-authored CLI bookkeeping.

The controller preserves one latest checkout baseline as non-credit evidence whenever semantic credit is invalidated. Initial `init`, every authority reconfiguration, and ordinary migration seal their lock-bound observed inventory in the ordinary non-passing Plan artifact shape. The exact first-slice Engineering migration exception instead seals that same live inventory into its imported Plan/Slice credit. An accepted Engineering candidate remains sealed across the boundary into the next slice, and a questioned or blocked attempt retains its controller inventory until a fresh assignment replaces it. In inactive Engineering, a same-authority closed failed Review/QA candidate base is preferred only when it is strictly newer than both the retained candidate and the last completed-slice boundary. If an older Review/QA remediation candidate remains but its matching inventory was replaced by a later non-passing Engineering artifact, checkout verification may use only that strictly newer controller-validated artifact inventory; an equal, older, or absent baseline remains fail-closed against the retained candidate digest. Reconfiguration generation, authority binding, accepted-slice history, questions, and remediation gates prevent any retained record from advancing a phase. The status-derived reconfiguration command ID also binds the observed checkout digest. `status` and every mutation or exact replay validate the live checkout against the current epoch baseline under the state lock.

## Rework and readiness

After a Review or QA `fail`, the controller preserves the failing artifact and candidate in the closed remediation gate, invalidates engineering and every downstream artifact, and issues a writable engineering assignment based on that candidate. The repaired candidate must pass fresh Review and QA. A `blocked` outcome repeats its source phase after resolution; its compact retry capsule retains the matching blocked artifact and resolution even before any Engineering candidate exists, preventing unchanged unavailable-environment retries. A documentation change also routes through fresh Review and QA.

Schema-10 migration normally starts at `plan` and reruns every phase. It may start at `engineering` only when the legacy state is an implementation-stage `scope_expansion_hold` on the first ordered slice, its active Engineer lease has concrete lease/worker IDs, an immutable snapshot, and an owner-bound passed pre-edit proof but no prior Engineer run or completion marker, and its active slice, ordered slice IDs, approved plan digest, every slice's editable paths, lease paths, and hold candidate paths exactly match the supplied v2 slices. The controller then preserves ordinary Plan/Slice credit against the migration-time live checkout, retires the legacy lease/hold into a closed audit gate, and issues a fresh v2 Engineer; it never copies the old worker assignment. A missing snapshot, malformed identity, or any other conflicting boundary falls back to `plan` without trusted legacy candidate credit. A legacy candidate is never treated as current Engineering, Review, or QA evidence.

The runtime is replay-safe and compare-and-swap protected. Exact repeated commands are no-ops only while authority and the retained live-checkout baseline still match; `next` checks its recorded-generation intent before current-generation assignment defaults, preserving exact omitted-identity and explicit-identity lost-response replays. Conflicting, stale, or drifted writes fail without mutation. State replacement is atomic, and native process locks are released after a crash.

`ready` additionally requires a completed-slice prefix equal to the entire approved ordered slice list. It means production-ready candidate only; it does not authorize deployment, publication, spending, submission, or risk acceptance.
