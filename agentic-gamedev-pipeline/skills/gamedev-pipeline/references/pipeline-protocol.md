# Pipeline v2 protocol

This is the complete Director protocol for the sole runtime engine.

## Authority and phases

Approved requirements, specification, and development plan files are immutable authority for an authority epoch. `init` accepts exactly the authority keys `requirements`, `specification`, and `plan`, one compact safe ASCII run identifier, and at least one caller slice record with exactly `id`, `allowed_paths`, and `planned_commands`. The controller alone derives and stores each slice's fourth `read_paths` field from that approved plan slice's Context Capsule `authority_paths` plus `evidence_paths`; IDs must match exactly, paths are deduplicated canonical project-relative exact or terminal `dir/**` rules, and caller-authored read scope is rejected. `allowed_paths` remains the sole write authority. The run ID starts and ends alphanumeric, is at most 64 characters, and otherwise permits only dots, underscores, or hyphens. The same command can rebind changed approved authority or an old three-key live scope under generation CAS, restart planning, and retain the prior candidate/history as audit context. Sole runtime v2 has no `authority_recovery_hold`: a sanctioned upstream controller may reopen its own authority, after which `status` observes authority and checkout under the state lock and returns one exact `init` whose command ID binds the observed authority paths/bytes and controller-projected four-key slices. Execution recomputes and validates that binding under the lock; every other public mutation fails closed, and every replay fails closed, on drift or an old unsealed scope without a state write. Execute that `init` only after every changed upstream controller reports readiness for the exact current bytes; unsanctioned drift must be restored or reconciled upstream first. An active assignment may be interrupted only after the controller proves its checkout diff stays within the old assignment; pre-existing foreign drift yields the non-mutating terminal status `checkout_recovery_required` instead of an unusable `init`, and the fresh Slicer scope must cover interrupted Engineering paths. Authority path comparisons follow host filesystem case semantics, so spelling aliases never turn sanctioned authority drift into foreign checkout drift. Never edit controller state directly.

A suspected controller, runtime, skill, protocol, or state-transition defect is a mandatory incident stop. The Director and every worker stop the product run, publish bounded redacted evidence and the exact recovery prerequisite, and do not edit, patch, bypass, replace, or continue through the pipeline. Product-run activation is not maintenance authority. Only a new explicit user command may start a separate pipeline-maintenance task.

The seven phases are `plan`, `slice`, `engineering`, `review`, `qa`, `docs`, and `ready`. The controller derives every transition. Each ordered slice passes Engineering, fresh Review, and fresh QA before the next slice; documentation starts after the final slice. A passing phase is committed with `complete` and advanced with `accept`; a question or blocked outcome returns to the phase that produced it. Documentation changes must pass a fresh Review and QA before `ready`.

## Nine commands

- `init`: create a v2 run, or reconfigure changed approved authority/scope at a safe boundary.
- `status`: read the compact current view and its one controller-derived `next_action` without mutation.
- `next`: issue one bounded assignment for the current phase, deriving its canonical identity, task, access, checks, and Review target from controller state; compatibility identity flags may be omitted and must match exactly when supplied.
- `complete`: submit one semantic worker artifact; controller evidence is gathered independently.
- `answer`: record the Director's safest reversible authority-consistent assumption and invalidate the affected artifact.
- `resume`: resolve a gate; Review/QA failure routes to engineering remediation, while an external block returns to its source phase.
- `accept`: advance from the current passing artifact.
- `migrate`: retained fail-closed tombstone; schema-10 migration is unsupported by `git-tree-v1`, so archive legacy state/findings and run fresh Plan/`init`.
- `ready`: seal the live, independently reviewed and tested terminal candidate.

Exact flags belong to each command's `--help`; do not copy old command recipes into worker prompts.

The Director executes `status.next_action`; it does not invent command IDs, generations, assignment identities, output paths, access rules, checks, Review targets, gate/question IDs, or recovery reasons. The optional controller state path must resolve to one direct `.json` child of the exact project root's `.agentic-pipeline-v2` directory; an external, nested, symlinked, or reparse-point path fails before mutation. `controller_decision` actions include a policy for choosing a conservative product assumption without technical user input.

## Assignment and artifact boundaries

Only one assignment may be active. It exposes a controller-derived `artifact_schema` and one controller-derived `output_path` under `.agentic-pipeline/outputs/`; the worker follows that schema without reading runtime code, writes its semantic JSON only there, and `complete` reads only that exact path. Controller directories are never Git-tracked and are excluded from candidate tree construction, so semantic output cannot create candidate drift. Every retry uses a worker ID absent from controller-owned completed actor history, and Engineer IDs cannot be reused for Review or QA. The controller derives canonical read/write access, checks, and Review target again for every `next`; omitted or conflicting caller values never change the issued packet. Planning, slicing, Review, and QA receive no candidate write access. Engineering scope and checks come from the current slice. Documentation receives controller-derived project-relative write paths. Authority files are never writable.

Workers run only the scenarios supplied by the assignment. Engineering, Review, and QA read access is the deterministic deduplicated union of authority plus every completed/current slice's `allowed_paths` and sealed `read_paths`; a post-Docs Review also reads its exact changed Docs target paths. Engineering write access and Engineering/QA checks remain exactly the current slice's `allowed_paths` and `planned_commands`, and future slices remain unreadable. Review read access outside the target is evidence context, not audit scope. For `current_slice_implementation`, the small controller-derived `context.review_target.required_scope` equals `current_slice.allowed_paths`, while `candidate_changes` lists exact paths from the accepted Engineering controller changed paths. Introduced-defect and excess-complexity findings bind to those changed paths; outside them, only missing mandatory implementation inside the required scope or a direct regression caused by the candidate on a supported path or deterministic trace is eligible. For a post-Docs `documentation_changes` Review, exact Docs `candidate_changes` are both required scope and complete target. A worker never runs or reruns assigned planned-command argv itself. On `complete`, the controller runs that exact argv against the canonical live checkout and compares the Git candidate tree immediately before and after each process tree. Any candidate change fails closed before later commands and without a state commit; the controller does not roll bytes back. Ignored temporary, cache, editor, and ordinary log files are outside pipeline control and are neither redirected, classified, nor cleaned. The current runtime defines no controller scratch path.

A Review finding requires concrete current-candidate evidence, reachable supported game behavior or a deterministic code trace, material violation of mandatory approved behavior/acceptance or concrete target-added excess complexity, and a smallest correction inside the target. Theoretical or extremely unlikely risks, unsupported misuse, manual tampering, future-scale concerns, unrequested security hardening, style/nit/refactor preferences, optional cleanup, tests merely for completeness, and pre-existing unrelated issues are excluded. KISS/YAGNI rejects target-added abstraction, state, configuration, fallback, dependency, or lifecycle that authority does not need when a simpler sufficient implementation exists; it never requires additional generality or defensive infrastructure. Review passes with empty findings and stops once mandatory behavior, directly affected integrations, and minimal sufficient complexity are verified. It returns no suggestions or backlog. Questions are only for a direct authority contradiction that changes the verdict; `blocked` is only for a genuinely missing mandatory input or capability.

Read-only checks MUST NOT create any full or partial project/candidate copy. Materialized checkouts, clones, snapshots, worktrees, hard-link trees, reflinks, block clones, and copy-on-write checkouts are forbidden. Checks operate only on the canonical live checkout.

Each planned command and all descendants have one controller-owned lifetime. The controller proves containment capability before target code can run, terminates remaining descendants after every normal or timed result, drains output with bounded memory, records timeout return code `124`, and records controller launch or process-tree-control failure with distinct technical return code `125`. Windows uses a kill-on-close Job. Linux requires a successfully probed util-linux PID namespace (`unshare --pid --fork --kill-child=KILL`), trying direct capability before a user namespace mapped to the current user. A controller-owned wrapper installs `PR_SET_PDEATHSIG`; adapter death kills namespace PID 1, after which the kernel kills every namespace member even if it called `setsid` or scrubbed its environment. If this kernel containment is unavailable, or on another POSIX host, the controller returns `125` before launching the target; there is no PID scan, numeric kill, process-group heuristic, or permissive fallback.

Planned commands execute in order only through the first non-zero result. The controller compares the Git candidate tree before and after every executed command, including the failing command, and accepts only a complete all-pass list or the exact prefix ending in its first failure. With no tree drift, a non-zero result preserves the worker artifact unchanged and stores exact argv/return code/full stdout and stderr digests. Only failure evidence additionally stores a redacted and project-path-normalized stderr tail of at most 4096 UTF-8 bytes with explicit truncation/redaction flags; sensitive token/PAT/database-URL/DSN environment values and URI userinfo are redacted, while stdout, environment, cwd, and full stderr are never persisted. Worker `fail` keeps the ordinary worker-result gate and may carry the safe controller-failure capsule when a controller check also fails. Worker `pass` plus controller failure instead atomically closes the assignment, opens a distinct controller-result gate, grants no candidate or phase credit, and exposes `resume`; QA controller failure resumes in writable Engineering. A valid `blocked` artifact is accepted only after artifact, live-tree, CAS, authority, runtime, and replay preflight; it runs no commands, stores `commands: []`, creates no candidate or phase credit, and opens the ordinary worker-result gate with non-empty `blocker` and `required_action`. Public `complete`/`status` expose only the safe failure capsule under `next_action.gate.controller_failure` (one-based command index, return code, stdout/stderr digests, bounded excerpt and flags, and unexecuted-command count), and the same capsule is retained in the fresh remediation assignment context without argv or raw process context. Exact replay is a byte-noop and never reruns checks. Candidate-tree drift, authority or runtime drift, policy-file changes, forbidden changed paths, non-prefix evidence, success truncation, evidence after failure, and malformed excerpts fail closed without state mutation. Schema remains `2`; its sole live checkout model is `git-tree-v1`.

Workers receive semantic context, not controller bookkeeping. Accepted worker artifacts are deliberately small:

```text
plan:         outcome, non-empty summary, optional questions
slice:        outcome, summary, optional ordered slices and questions
engineering: outcome, summary, optional assumptions and questions
review:      outcome, findings[{text,severity,kind}], optional questions
qa:          outcome, checks, optional questions
docs:        outcome, summary, optional questions
blocked:     every role also requires non-empty blocker and required_action
```

`outcome` is `pass`, `fail`, or `blocked`. Questions are concise strings. Mechanical checkout evidence, process results, replay protection, and atomic state commits are controller-owned and must not appear in a worker artifact.

After authority reconfiguration, the Director executes the exact `init` action with the prior safe slice list and controller-recomputed read binding. Planning revalidates intent, and the Slicer may replace the three caller-owned fields through its semantic artifact only when its ordered IDs match the approved plan; the controller re-derives `read_paths` before reduction. This keeps `status.next_action` exactly executable while leaving product decomposition with the planning role rather than caller-authored CLI bookkeeping.

The controller preserves one latest `candidate_tree_oid` as non-credit evidence whenever semantic credit is invalidated. Initial `init`, authority reconfiguration seal that lock-bound tree in the ordinary non-passing Plan artifact shape. Accepted Engineering and Docs candidates store exactly `base_tree_oid`, `candidate_tree_oid`, sorted literal `changed_paths`, authority/runtime digests, violations, and command receipts. An active assignment base contains only its `candidate_tree_oid`. In inactive Engineering, a same-authority closed failed Review/QA candidate base is preferred only when it is strictly newer than both the retained candidate and the last completed-slice boundary; a newer non-passing Engineering artifact can provide that evidence without granting credit. Reconfiguration generation, authority/runtime binding, accepted-slice history, questions, and remediation gates prevent a retained record from advancing a phase. The status-derived reconfiguration command ID binds the observed tree OID. `status` and every mutation or exact replay validate the live candidate tree against the current epoch baseline under the state lock. Legacy schema-2 physical-inventory states fail closed with fresh-`init` guidance; there is no dual model or full-inventory fallback.

## Rework and readiness

After a Review or QA `fail`, the controller preserves the failing artifact and candidate in the closed remediation gate, invalidates engineering and every downstream artifact, and issues a writable engineering assignment based on that candidate. The repaired candidate must pass fresh Review and QA. A `blocked` outcome repeats its source phase after resolution; its compact retry capsule retains the matching blocked artifact and resolution even before any Engineering candidate exists, preventing unchanged unavailable-environment retries. A documentation change also routes through fresh Review and QA.

Schema-10 import and reconstruction do not execute. The retained `migrate` surface always returns the stable unsupported/fresh-init error and never writes controller state.

The runtime is replay-safe and compare-and-swap protected. Exact repeated commands are no-ops only while authority and the retained live-checkout baseline still match; `next` checks its recorded-generation intent before current-generation assignment defaults, preserving exact omitted-identity and explicit-identity lost-response replays. Conflicting, stale, or drifted writes fail without mutation. State replacement is atomic, and native process locks are released after a crash.

`ready` additionally requires a completed-slice prefix equal to the entire approved ordered slice list. It means production-ready candidate only; it does not authorize deployment, publication, spending, submission, or risk acceptance.
