# Director control return

Apply only when a Director supplies `control_binding`. Standalone stage calls keep their existing public result. This host-message wrapper changes no semantic artifact, native handoff, approval, role permission or controller API. Workers read only [Worker return](#worker-return) and their supplied binding/return route. Directors use [Caller binding and dispatch](#caller-binding-and-dispatch) and [Consume worker events](#consume-worker-events); stage ingress is conditional.

## Caller binding and dispatch

The Director allocates a strictly increasing `request_id` within its run and retains the physical recipient from the host. This host correlation never replaces a native command/action ID. Send exactly one binding variant:

- Native assignment: `{kind: "native_assignment", request_id, assignment_id, worker_id}`. Copy assignment/worker IDs from the issued assignment; reuse this binding through its check/technical continuations. A new check's opaque command `--id` is separately allocated by its authorized invoking worker or relay Director under [active checks](execution-contract.md#check-inside-active-engineering-or-qa); it is not a new native assignment or recipe identity.
- Caller task: `{kind: "caller_task", request_id, task_kind, parent_request_id}`. `task_kind` is `requirements`, `specification`, `development_plan`, `recipe`, `semantic_answer`, `recovery_evidence` or `maintenance`; `parent_request_id` is the retained request being served, or `null` for first ingress. Do not add native IDs, even when this physical specialist has a separate native role alias. Native `question_id`/recovery binding belongs in the supplied task input, not invented assignment fields.

For a native assignment, forward the generated `assignment_delivery.dispatch` unchanged together with `control_binding`, actual permission/check-grant sources and the caller/owning-parent return route below. The descriptor already supplies native IDs, project/cwd, launcher, versioned input, scope/output and action/stop boundary. Its recipient uses the generated bootstrap and needed semantic-section/work-item readers under [Worker read route](delivery-contract.md#worker-read-route), and reads role instructions; the Director neither reads those bodies nor reconstructs them. `output.write_authority` describes the issued exact terminal-artifact right, independently of product `access.write`; `controller_mutation_authority` still requires a separate bounded grant. `launcher_argv` plus `controller_args` supplies invocation syntax only, not command permission. A conflicting retained runtime/root binding is a control error. Use full or eligible same-owner delta under [Update the same worker](delivery-contract.md#update-the-same-worker).

Use this bounded caller template for caller tasks or legacy native delivery without a descriptor, filling values from existing authority/native output:

> `control_binding: <exact binding>`. Role instructions: `<existing role locator and applicable section>`. Task and stop boundary: `<authorized stage, issued assignment, or one bounded question>`. Project/cwd: `<absolute native project_root, forwarded unchanged; for caller tasks use the authorized task root when project file access is needed>`. Inputs: `<unchanged delivery/native handoff and exact source/version locators>`. Permissions: `<actual authorization sources, scope, exclusions, actor/model constraints>`. Control route: `<native-check grant or relay when applicable; exact native launcher argv/root/feature for a granted command, never inferred from the worker cwd>`. Return route: `<actual caller and owning/spawning parent from retained host ownership; direct with an established completion-observation path, otherwise owning-parent relay>`. Follow this control-return contract outside your unchanged semantic artifact/native stage handoff; consume required input completely before work.

For native assignments, copy delivery `project_root` unchanged as the worker's explicit cwd on initial dispatch and continuation. Relative product/source/output paths are rooted there; retain exact absolute role-instruction locators separately. A legacy packet lacking root needs the retained controller-bound root or one permitted status restore before file work, never an inferred directory. Missing/conflicting root is a bound clarification, not permission to search for a substitute project.

`followup_task` does not reparent a reused worker. Direct cross-parent reuse is allowed only when the actual caller has an established real host path to observe that worker's completion independently. Name that path and the recipient in the return route; the worker sends its necessary bound event directly there with `collaboration.send_message`. Otherwise send the bounded request through the existing owning/spawning parent: it reuses the worker and forwards necessary informative events while live; for a terminal/task result it consumes the child result and actual host completion before returning the requested result to the caller under its existing caller-task binding. Caller and parent identities come from retained host ownership, never guesses. If neither supported route is available, use the existing factual blocker route, not an invented subscription/wait API. This relay starts no new stage or manager. The same-parent route sends informative check events directly and uses its existing event/final delivery for terminal results, without an extra acknowledgment or duplicate send. Return routing is dispatch metadata outside the unchanged binding/event wrapper; it supplies no native IDs or new authority.

An idle recipe question uses the existing responsible Planning role within its delegated scope, not a new preparer or a new Planning cycle. If no physical owner exists, the Director may create that existing role only when its delegation is already authorized. Stage readiness never supplies missing activation/approval authority.

Keep one active control binding per physical owner. Do not replace an unrelated active assignment/task with a caller question; retain the bounded request until that owner is eligible or route it through its existing owning parent. A retained inactive native alias never supplies IDs for a caller task. Same-assignment check, correction and resume continuations keep their existing binding.

## Worker return

For each necessary event return `{binding: <unchanged>, event_seq: <positive integer>, event: <below>, payload: <only that event's data>}`. Start `event_seq` at 1 per binding and increase for a new event; repeat exactly the same sequence and payload when repeating an event. Host sender identity is authoritative for physical ownership. An event informs its recipient; it does not by itself end the host turn. During an active native-check grant, send `check_result` to the established control recipient with `collaboration.send_message` and continue in the same host turn after full fresh delivery consumption, without acknowledgment or another unchanged grant. When the return route uses an owning-parent relay, that parent forwards this informative event while the worker remains live. Missing delivery/route/context or a required decision/error boundary pauses affected work; terminal/task-result events retain their stop and completion rules. Commentary/progress is not a control event and requires no acknowledgment or routing.

| Event | Payload and boundary |
| --- | --- |
| `terminal` | Native assignment only: exact `artifact_path`, factual `quiescence`, and latest native cursor/receipt/delivery locators when changed. Stop owned activity. This is not host termination or native PASS proof. |
| `check_request` | Native assignment only: `quiescence` and optional `collect_independent` request. Pause for required relay or missing grant/access; do not repeat this request for each check under the unchanged active grant. |
| `check_result` | Native assignment only: unchanged actual native result/cursor/delivery and factual quiescence at the check after consuming the refreshed packet. Informative within the active grant: resume permitted work in the same host turn without acknowledgment. Assignment/grant remain active; this is not terminal output or phase PASS. |
| `technical_request` | Native Engineering only: `operation` (`technical-observe` or `technical-decision`), exact action text or permitted request path, and quiescence. Keep ownership; no terminal artifact. |
| `question` | Exact question, intended existing specialist/user decision boundary and necessary source locators. No worker claim creates user authority. |
| `request` | `request_kind: read_admit` with exact existing path/reason, or `request_kind: capability` with actual missing/resolved prerequisite and evidence. This requests the existing route; it grants no access/recovery authority. |
| `task_result` | Caller task only: unchanged existing native stage handoff, or the requested exact answer/serialized recipe/recovery evidence/maintenance result. Preserve its source bindings, truth and unresolved outcome. Stop that caller task; never call runtime `complete`. |
| `control_error` | Exact native error or factual host/capability failure; keep its original category/text and current binding. No guessed retry or fabricated semantic result. |

On the next necessary event only, optionally add `retained_baseline: <packet_digest>` outside `payload` when the complete applicable packet content is consumed and still retained, or `null` if lost. Never send a separate acknowledgment ping. Without an established eligible baseline, the caller uses full delivery.

## Consume worker events

The Director retains current/just-completed binding, consumed sequence/fingerprint and at most one pending event per owner. Exact consumed duplicates make no call; pending duplicates remain one pending item; events from an older superseded request or below consumed sequence are ignored. A conflicting payload at the current correlation gets one bounded reconciliation, not repeated dispatch. Old cursor data never replaces a newer cursor. A completed host turn without a usable wrapper permits one same-owner correction; do not invent assignment/worker IDs, generation or mechanical `next_action` IDs, or reauthor stage output. Correlated `task_result` is forwarded only to its pending caller route, never interpreted as native terminal completion. Terminal and task-result consumption wait for actual completion: direct returns use the established host path; relayed returns wait for the owning parent to consume child completion. Informative check events do not wait for worker completion or invite a followup while it is live. Worker quiescence prose replaces neither required completion observation. Final/lifecycle delivery does not create another event sequence, reroute an already consumed event or require another semantic response. If the event was already delivered directly to that caller, the spawning parent does not forward another copy on final delivery.

## Stage ingress

Load this section only for an authorized upstream stage or a bounded caller task; ordinary issued production assignments do not require it. Reuse an eligible owner or create only the already-authorized existing role using the caller binding/template above. For a fresh owner read only its applicable [stage-session](agent-model-policy.md#stage-sessions) or [delegated-role](agent-model-policy.md#delegated-roles) model row, preserving overrides. No competing writer or new preparer role. Missing role/stage authority remains an exact decision, not implicit approval.

| Authorized task | Exact input and existing owner contract; result boundary |
| --- | --- |
| Initial Requirements | Actual user task/source and [Requirements SKILL](../../gamedev-requirements/SKILL.md). No preceding readiness or runtime status. Return its existing PRD handoff unchanged. |
| Specification | Full exact `PRD_READY: yes` handoff: canonical path, approved revision/SHA, feature/workflow; [Specification SKILL](../../gamedev-specification/SKILL.md). Return exact native `SPEC_READY` path/hash/source evidence, including any unresolved gate. |
| Development Plan | Exact PRD and current SPEC handoffs above; [Development Plan SKILL](../../gamedev-development-plan/SKILL.md). Return unchanged `PLAN_READY` handoff: canonical path, mode, submitted/approved SHA, source paths/hashes and actual gate. |
| Production setup | Approved PRD/SPEC/PLAN triple and available serialized setup fields. Director copies exact fields under [Authority and phases](pipeline-protocol.md#authority-and-phases). No new Planning artifact or repeated approval merely for mechanical copying. |
| Bounded recipe, answer or recovery evidence | Exact question/native source binding and actual permissions to its existing responsible specialist, normally Planning for recipe serialization. Keep `parent_request_id`; inactive native aliases supply no task IDs. Return only requested exact `task_result`, without restarting a stage or changing approved obligations. |

Preserve complete native handoffs, not a new semantic schema. Stage owners run their own validation/approval/readiness commands; their advisory `NEXT_ACTION` creates no activation or approval authority.
