# Technical decisions

This is the shared policy for unexpected situations during development and for every role that later implements, reviews, tests, documents, or revises that work. It is platform-neutral. It does not activate a stage or grant a role another role's product write access.

## Resolve before escalating

An unexpected tool response, error, incidental change, or inconsistent technical instruction starts an investigation, not an automatic terminal blocker. Establish the cause, affected work, available capabilities, and actual consequences. Check a permitted alternative when there is evidence it can resolve the problem; do not repeat a failed action without new evidence. Preserve unrelated user work.

The Engineer may correct technical details, local operation order, and incidental implementation needs when the correction preserves requirements, product choices, acceptance obligations, and approved technologies. A plan describes the intended execution; a technical mistake in that execution is not itself a reason to reopen upstream stages. Establish dependency consequences before changing order. A file extension, tool name, or claim that an editor normally generates files is not proof that a particular change is harmless.

The user decides changes to requirements, product choices, or approved technologies, including a conclusion that the feature cannot be implemented with those technologies. Present the concrete conflict and smallest alternatives. The user may approve a local amendment or require revisiting upstream documents; neither outcome is inferred from silence. Record the exact authorization and its scope. A technical decision cannot create product authority, waive mandatory acceptance, or authorize a new external effect.

Resolve a technical situation within existing access directly. If resolution needs a controller-governed change to scope, command order, or checkout reconciliation, use the sanctioned public technical-decision action before continuing that affected work. A journal entry alone never changes access, accepts foreign changes, or bypasses a gate. A suspected pipeline/controller defect still follows the separate Controller incident stop.

For that action, the Engineer pauses the affected mutation and sends the Director a bounded request, without returning a terminal artifact or surrendering assignment ownership. The Director operates the public command and sends the refreshed active assignment to the same Engineer. Before an editor/tool action that can create persistent incidental changes, request `technical-observe` while the scoped checkout is valid. Its before-action observation allows later exact reconciliation; it cannot be fabricated after the unexpected changes or prove ownership against a known concurrent writer. Never adopt unrelated/user edits as incidental work. Command mechanics and the permitted workflow-local request file are defined in [pipeline protocol](pipeline-protocol.md#technical-action-interface).

Verify the resolution through relevant available evidence and identify what remains unverified. Planned commands remain controller-owned: do not execute or rerun their argv in a worker. Distinguish a resolved obstacle from a passing acceptance check. Continue independent safe work when one prerequisite remains unresolved. Return `fail` for attempted work or a reproduced product/test failure that needs technical repair; reserve terminal `blocked` for a genuinely unresolved prerequisite or user-owned decision after this assessment.

## Current journal

Keep one current feature-local journal, separate from accepted product decisions and the planning `DEC-*` ledger. Its canonical location is `.agentic-pipeline/Workflows/<feature>/pipeline-state.json#technical_decisions`. The controller owns persistence; workers use only the issued semantic artifact or public technical-decision action, never edit controller state directly. Follow the issued schema for exact fields. A journal reference supplies the path and current content digest; read only its current entries rather than forwarding other controller bookkeeping.

Record every encountered blocker, including one resolved autonomously before a terminal outcome. Use a stable ID for the situation. A short factual entry contains the situation, current decision, basis, checks/evidence, downstream consequences, and an optional exact overridden artifact reference. The basis states why the decision is within authority, or cites the user's actual approval. The override identifies the source revision and exact location plus the technical position being replaced; the decision states the replacement. An unresolved situation records the missing decision/action and unexecuted checks honestly.

The semantic `technical_decisions` array uses `{id, situation, decision, basis, checks, downstream, overrides?}`. IDs are stable `TD-*` strings; all other fields are non-empty text except `checks`, a list of actual evidence strings, which may be empty when nothing could be verified. `overrides` is omitted when no artifact position is replaced. Controller-sealed execution metadata is not worker-authored. For a readable report, render each ID with Situation / Decision / Basis and checks / Downstream, adding the exact override only when present; do not create a second writable journal. The controller records a terminal blocker fallback when a blocked artifact omits its entry; this is no substitute for the worker's cause analysis and does not capture a silently resolved blocker.

Correct a wrong or outdated decision by overwriting the same entry in place. Do not append cancellation, supersession, or rejected-alternative chains. Repeated occurrences with the same cause and resolution update the existing entry. Keep useful diagnostic facts and evidence references, not raw tool transcripts or private reasoning. Do not silently omit a blocker merely because a retry or correction succeeded.

Only an applicable, authorized and evidence-supported technical correction governs the exact position it identifies; the rest of the approved artifact still applies. A recorded decision is not a waiver. Reassess applicability when the source revision, candidate, or relevant evidence changes; do not relocate an old override by guesswork. Refresh affected downstream work and invalidate any dependent stale assessment through the controller's ordinary routes. Merely reading an old passing assessment does not verify the new decision. A Review/QA entry update may describe evidence and the actual candidate; a proposed remedy requiring product or governed execution changes must return `fail`, not a passing assessment of an unimplemented correction. Only the sanctioned Engineering action changes an execution overlay.

## Role responsibilities

- Engineer: investigate, resolve within authority, verify consequences, and submit the current entry. Include decisions needed by later implementation and verification.
- Review: read decisions relevant to the issued target and independently assess authority, cause, consequences, evidence, and the candidate. Do not fail solely because execution differs from the original technical plan; do not pass because the difference is logged. A concrete unsupported or unauthorized decision affecting the target is eligible for correction. Use the existing `fail` remediation route for technical defects and explain the smallest sufficient repair; do not create an approval loop or broaden the audit to unrelated entries.
- QA: use relevant decisions to understand setup and affected dependencies, then execute the assigned acceptance scenarios. Record actual observations; the journal cannot close `not_run`, remove an identity, replace production-path evidence with substitutes, or change expected product behavior. Use existing technical repair routing when the resolution is wrong. QA and Review remain read-only to persistent product files.
- Director: provide the current journal context, preserve decision provenance, consume updates through the controller, and follow its resulting action. Let Engineering, Review and QA resolve technical disagreements through ordinary remediation. Escalate the specific remaining user-owned decision, not all technical work. Show a compact readable account of current decisions when reporting or handing off; do not copy raw controller state into worker context.
- Documentation: reconcile relevant decisions with approved intent and verified behavior. Do not restore a superseded technical instruction or make a new normative product promise.
- Requirements, Specification and Planning on reentry: read current relevant decisions as evidence, reassess them against the stage's authority, and incorporate valid corrections through that stage's sanctioned revision process. Requirements remain confirmed-only. Do not promote an engineering choice into a product requirement or a `DEC-*` authorization. When an updated source incorporates a correction, update its existing journal entry's applicability through the permitted owner instead of retaining a second competing instruction.
- Advisory roles: consider relevant journal evidence only within their explicit assignment; they acquire no runtime transition, product edit, or waiver authority.

Fresh workers, replacements, repeated stages and post-documentation checks receive current relevant entries, their locator and necessary source/evidence references. Count delivered entries against ordinary context budgets. Never rely on a previous conversation or send superseded versions and unrelated history. A missing entry needed for the current judgment calls for retrieving it, not guessing its contents.

When `context.technical_journal.requires_current_journal_read` is `true`, the supplied entries are an incomplete projection: before implementation or judgment, retrieve the canonical current `technical_decisions` map at the supplied journal locator and select the entries relevant to the assignment. This read is mandatory even if the visible entries appear sufficient; a corrected older ID may be outside the projection. Use the current binding, do not infer omitted content, and deliver the relevant full entries and necessary evidence to any delegated reader. Do not forward unrelated controller state or superseded versions. The Director must include this required read in fresh and replacement handoffs; a pointer alone does not count as delivered decision evidence.

## Delivery continuity

The runtime preserves complete current entries and their text. Use the [delivery contract](delivery-contract.md) for full initial packets and updates to the same recipient; do not resend unchanged entries after each technical action. A new worker or lost context requires the applicable full content. The legacy `requires_current_journal_read` signal also covers truncated fields or a nonmatching journal digest, not just omitted IDs. Recover from the canonical current source before implementation or judgment; missing or unbound content never grants authority or credit.
