# Active checks and targeted recovery

Read only for initialization, active diagnostic checks or the named recovery. Exact public CLI flags come from the pinned launcher's command help. These routes keep the seven phases, single writer and candidate/authority guards.

## Resolve recipes and prerequisites once

This is a bounded task of the existing authorized Planning/recipe owner. Read [Source and binding](qa-acceptance-contract.md#source-and-binding), [Active authority during normalization](qa-acceptance-contract.md#active-authority-during-normalization), [Manifest](qa-acceptance-contract.md#manifest) and [Producer feasibility](qa-acceptance-contract.md#producer-feasibility) when extracting or preparing the approved methods; QA result construction is not part of this task. Resolve those bindings and immediate prerequisites before Engineering starts. An embedded approved definition is read automatically; for unchanged older documents, the existing authorized specialist serializes their exact assertions/methods into a workflow-local manifest for `init --qa-contract`. Director forwards that artifact without interpreting methods or inventing equivalents. Verify the actual result/capture/binding/read channel, not an unimplemented feature, and retain current prerequisite evidence. New workers receive the sealed definition instead of recreating it; a missing capability never waives acceptance.

Before implementation, copy already serialized exact approved/native/setup argv and ordered slice fields mechanically. If an approved method exists only as prose and needs semantic/tool mapping, the existing authorized responsible specialist, normally Planning, supplies that bounded serialization using observed project tools; the Director forwards the question/result without choosing checks, technology or dependency closure. Reuse/create only that already-authorized existing role through a [caller task](control-return.md); do not require a new Planning artifact, repeat approved Planning or infer redelegated approval. The specialist first uses exact tool/executable/resource locators already supplied by the plan or setup, before general discovery. Reuse compatible prepared method/contract structure and stable probe locators subject to current binding checks; never reuse old product PASS or session-local handles. Probe only immediate invocation/result/capture/independent-read capability and containment, without implementing the game or repeating the full acceptance matrix. Capability evidence must cover the actual access surface, launch scheme/origin and session. An executable or generic test page does not prove the product entrypoint; when that entrypoint is not yet available, retain it as unverified and perform the cheapest actual startup when it exists. Keep implementation prerequisites distinct from the plan's final manual/device identities. The specialist selects an appropriate timeout and retains the recipe for reuse.

Optional `init --verification <workflow-local manifest>` seals version 1 recipes: `slices` maps each slice ID to entries with `id`, exact `argv`, `kind` (`deterministic` or `environment`), `timeout_seconds` and `independent`. The same manifest carries `pure_documentation_paths` and `confirm_approved_plan`. These fields do not change approved methods, paths or identities; argv must match the supplied approved-method serialization. Choose deterministic only when repeatability and dependencies support it. No recipe means conservative environment-sensitive execution. Do not label input fixtures, runtime config or executable instructions as pure documentation merely because their extension is text.

A deterministic recipe additionally needs explicit `input_paths`: the complete exact list of extra file dependencies outside the bound candidate/executable, including any relevant ignored or external configuration/data/module files. Relative paths resolve in the project; an external dependency uses its explicit absolute path. Wildcards and duplicates are rejected. An explicit empty list means the reviewed recipe genuinely has no extra file inputs, not that unknown dependencies may be ignored. Missing `input_paths` disables reuse even when `kind` says deterministic. The controller hashes declared inputs before and after execution and before reuse; it does not inventory all ignored files or prove hermeticity from an assertion. If the closure, external state or repeatability is uncertain, use environment-sensitive execution. Duplicate argv may not carry conflicting execution semantics.

`confirm_approved_plan: true` requests machine no-op Plan/Slice confirmation only when source validators, producer feasibility and retained-scope/conflict guards succeed. It does not approve a missing PRD/SPEC/PLAN, decide semantics or skip actual replan work.

## Artifact and execution record I/O

These helpers preserve files under the selected feature workflow; they grant no product edit, external execution, controller transition or semantic PASS. Use the supplied launcher/global root/feature argv. Keep large assessed JSON and raw tool responses in authorized files, not inline shell strings. Input staging needs its own existing write authorization; a helper's exact output right does not authorize arbitrary staging locations. A request/result/environment file locator is separate from paths inside that file: when a path error names the request itself, correct that locator rather than rewriting its `input_paths`.

- `artifact-validate --source <existing-json-file> --assignment-id <issued-id>` checks the current issued artifact schema and returns independent formatting errors together, without product tests or a state transition. It cannot verify an observation's truth.
- `artifact-write --assignment-id <issued-id> --source <existing-json-file>` uses the same validation and common UTF-8 serializer, writing only the current assignment's exact terminal output. Invalid input returns errors without writing it. Use this as the last owned write; native `complete` still performs acceptance guards.
- `evidence-begin --request <json-file>` captures the real before-binding. Product capture requires the exact active `assignment_id`, `record_id`, `invocation` (object naming the actual `channel` and request), `environment` (nonempty object of stable identity/version/prerequisites) and `input_paths` (exact relevant files). For the existing bounded recipe task before runtime initialization, omit `assignment_id` and add `preflight: true`, the exact `project_root`, `feature` and `authority_paths` with `requirements`, `specification`, `plan` paths. This binds current approved sources and candidate; a preflight record never proves product acceptance.
- After the authorized execution, retain its actual raw response immediately and call `evidence-record --record-id <same-id> --result <raw-response-file> --environment <after-environment-json>`. The helper records after-binding and input hashes with the original bytes under workflow `Evidence/<record-id>`. Changed required inputs remain visible and grant no current proof. Dynamic expected state transitions belong in the raw result/observations, not the stable environment object.
- `evidence-read --record-id <id>` returns the immutable record and raw-response locator with integrity validation. Select its needed subtree with `--pointer <JSON-pointer>` before display, using shared `--format text --assemble` or saved-output reading for a large selection. Use its `execution-evidence:<id>` reference, optionally a precise `#case-or-observation` locator, in semantic evidence. Read the actual referenced observation; metadata alone proves no behavior. Recover this same saved record after another run or console cleanup instead of rerunning an already completed action.

For the retained raw response, `evidence-read --record-id <id> --raw-file <exact-recorded-filename> --pointer /value/<needed-field> --format text --assemble` selects a JSON field before rendering. Take the filename and field from the actual record/result; do not guess a console or profiler envelope. A non-JSON UTF-8 response remains exact text under `/value`. Its original bytes, digest and origin remain in the immutable record regardless of the displayed selection.

Record IDs bind one actual invocation. An identical retry can recover the same record; different bytes or inputs need their own actual invocation identity. Never fabricate a missing before-state or overwrite a prior record to match a later candidate. Controller-run checks preserve their own execution records; callers do not relabel an external tool result as a controller receipt. [Preserve execution evidence](interaction-evidence.md#preserve-execution-evidence) owns the candidate order and shared assertion mapping.

QA uses [Incremental assessment](qa-acceptance-contract.md#incremental-assessment) to prepare full group obligations/producers, save independently evaluated rows and finalize through this writer. The generated source/receipt/capture metadata supplies provenance; observations and comparisons remain QA-authored.

A capture/presentation failure does not authorize reexecution. The same controller action ID recovers its saved terminal attempt/result, or stops on an unfinished attempt whose effect is unresolved; it never automatically repeats that side effect to recreate missing output.

## Check inside active Engineering or QA

At eligible dispatch, use worker-initiated native check when the exact pinned invocation, permissions and host/tool access are established and no actual policy requires relay; otherwise use Director relay. Retain the choice, exact assignment/caller binding, owner, root/runtime and permission sources in the existing handoff. A grant lasts for that unchanged binding, including ordinary check results and in-scope corrections; a new assignment/caller binding needs its own grant. Preserve authorized invocation-environment overrides without exposing secrets or weakening environment/reuse semantics.

The grant permits `check` and the read-only status/assignment-export/assignment-read/legacy delivery-read operations needed to consume or diagnose its result. It grants no lifecycle, recovery, journal, direct planned argv or other mutation. Invocation syntax is not authority. The Director performs no simultaneous workflow mutation or product edit while the grant is active, including between checks. This cooperative grant is not physical-agent authentication.

For feedback, finish and pause all owned mutation, processes and shared editor/player activity. Use the supplied separate launcher/root/feature argv and `check --with-delivery --id <new-command-id> --expected-generation <returned-current-generation> --assignment-id <issued-id> --quiescence <actual-pause>`. The invoking worker (or relay Director) allocates that opaque command ID once per new logical check; it is neither a recipe/check ID nor `next_action.command_id`. Candidate edits and a completed result permit a new logical check under the same grant with its latest returned generation. An uncertain-response replay retains the original ID and exact arguments.

Keep the complete original host result and request, including running cell/session handles. Wait for actual terminal completion through that handle; empty stdout, a yielded tool or outer-cell completion does not prove an inner command ended. [Command transport recovery](director-runtime.md#command-transport-recovery) supplies the exceptional host details. While the invocation runs, remain paused and wait; no duplicate check or status progress probe.

Consume the generated complete [Check delivery](delivery-contract.md#check-delivery): current binding, diagnostic return codes, failures, pending IDs and changed required instructions/decisions. The controller alone chooses and runs sealed planned argv. Recorded CLI success or partial results grant no PASS. A known committed result with a presentation failure is recovered by its returned read argv, not another check. Use returned cursors only. Unexpected owner/assignment/candidate binding or a known CAS, authority, runtime, containment, scope or delivery error pauses for the Director; it does not permit guessed fields or a broader retry.

Under the unchanged active grant, send the informative `check_result` through [Worker return](control-return.md#worker-return), then continue authorized work in the same host turn after fresh input is consumed. It needs no acknowledgment, redispatch, new grant or terminal artifact. QA cannot repair the candidate. Relay/missing access, real decision/error, context loss and terminal output keep their required pauses; resolve the actual boundary before restoring the same grant. Relay needs quiescence, not host termination. A terminal artifact must be consumed before another check and cannot be deleted to reopen work.

Review and QA use current controller-derived `context.machine_checks`, including exact durable record locators, and `pending_check_ids`. Review inspects actual evidence within its target and seeks missing existing locators through the current owner; it never executes planned argv. QA obtains missing applicable machine evidence through this grant/relay before its semantic result, never claiming a later `complete` execution in advance. Receipts prove only their real cases and approved methods; separate manual/device observations remain mandatory. Native granting execution retains conservative reuse, candidate containment and environment-sensitive reruns.

Use `--collect-independent` only for sealed independent checks while prerequisites and containment remain valid. A genuinely uncertain response can replay the original request once while quiescent after no invocation remains live; known committed output is read instead. Existing public recovery and terminal rules remain unchanged.

## Resolve an unchanged failed attempt

When Engineering finishes a failed attempt without changing its assignment-entry candidate, the native controller may consume that artifact and return `next_action.result=no_progress_resolution_required` instead of another assignment. This is an idle clarification hold, not a false PASS, worker deadline, retry quota or permission to change product authority. It applies to the current work basis; summaries, new command IDs and repeating the same checks do not supply a correction. Direct `next`/`step` and unchanged reset paths cannot bypass the hold. A useful changed candidate and a truthful proof-only pass retain normal independent Review.

This is an automatic internal route, not a user approval gate. Follow the action's responsible-role metadata through the existing bound caller-task route. For a disputed Review residual, use the existing Reviewer with the current exact conditions, failure, prior attempted assessments and source locators; for an initial failure without Review findings, use the existing Engineering owner to identify the concrete missing fact/next correction. The specialist states what the existing evidence establishes, what remains wrong/unproved, the permitted next correction and how it addresses the prior failed approach. Do not ask the Director to interpret code, manufacture a counterexample or waive a condition. Incomplete or duplicate clarification returns to that existing specialist; only an actual missing authority decision or unavailable access/capability goes to its authorized resolver or user.

The returned action supplies `question_id`, command ID/generation, `no_progress_binding`, affected condition pairs and `resolution_schema`. Copy the binding unchanged into one retained workflow-local JSON packet. The specialist supplies its `kind` (`clarification`, `counterexample` or `prerequisite`), a relevant nonempty subset of affected pairs (or `[]` when none), source evidence rows `{path,sha256,observation}`, and the exact permitted next correction in `answer`. Grant only the exact packet output if the caller task must write it; product scope and command permissions remain unchanged. Evidence must identify actual readable source versions bound to the held candidate or sealed authority. Arbitrary new workflow reports, copied receipts, Delivery, state or failure-output wrappers do not become source evidence by acquiring a new name or SHA. A materially changed prerequisite follows its existing sanctioned capability/reconcile/rebind route; do not simulate that change with a report.

Submit `P answer --id <A.command_id> --expected-generation <A.expected_generation> --question-id <A.question_id> --resolution <same-workflow-packet-path>`. Ordinary `--text` cannot release this hold. The controller validates project/run/work binding, source versions, permitted evidence scope and duplicate assessment identity; request IDs, path aliases or wrapper nonces do not make an identical assessment new. Unchanged source bytes may support a genuinely different condition-bound clarification. Distinguishing meaningful reasoning from paraphrase remains the independent specialist's responsibility, not a hash's proof. If an assessment is rejected or merely repeats the attempted basis, keep the internal clarification active with its existing owner and exact rejection. Do not auto-redispatch identical work, fabricate evidence, reset the run or ask the user to settle a technical misunderstanding.

A consumed resolution grants fresh work, not finding closure, product authority or phase credit. Follow its returned native action; only a newly issued assignment resumes Engineering with complete current work and applicable resolved clarification. If that attempt again fails unchanged, the native hold applies again and the prior resolution cannot be replayed to release it. Preserve current cursor and exact packet bytes for ordinary CAS/replay handling. Independent Review and QA remain required.

## Choose the narrow recovery

- Malformed artifact: native worker-validator origin is `artifact_format` with original error text. Send the exact rejection to the same owner/assignment once for truthful output correction where sufficient; semantic missing work remains that role's work. Never invent checks, evidence or PASS or duplicate the validator in Director.
- Stale action: refresh the cursor or replay the exact uncertain action; no product rework solely for CAS.
- Product/check failure: same Engineer, typed bound failure and current findings; independent Review/QA remain downstream.
- Needed read dependency: `read-admit --id --expected-generation --path --reason` requests one exact existing in-project non-control source. It grants no write access, review target expansion or foreign workflow access.
- Resolved external capability with unchanged dependencies: blocked status exposes terminal `next_action.command=recover-capability`, its exact `command_id`, `expected_generation`, `capability_binding` and required evidence fields. Keep the phase blocked until a real prerequisite change is evidenced. Copy `capability_binding` unchanged as `binding` into one workflow-local packet; the authorized specialist supplies nonempty `prerequisite`, `resolution`, `evidence`, `unchanged_dependencies` describing the real change. Then use `recover-capability --id <returned-command-id> --expected-generation <returned-generation> --evidence <same-workflow-json>`. The controller checks the exact blocked result and unchanged authority/runtime/candidate/scope/decision binding. It archives the blocked result and preserves valid upstream evidence. The automatically generated blocker journal entry is archived with that result and its prior value restored; genuine worker decisions are preserved. For blocked QA whose real decisions invalidate Review, the existing semantic guard selects Review before fresh QA. It grants no phase PASS, blind retry or waived identity. Do not substitute ordinary `init` for this route on unchanged bindings. Changed authority, runtime or product evidence keeps its existing public recovery route; a refused narrow recovery never authorizes a broader fallback.
- Explicitly authorized external edits: idle `reconcile --id --expected-generation --packet <workflow-json>` binds the observed candidate/generation and each exact changed path's authorization/provenance. This route works after an accepted slice when there is no active assignment; it does **not** require a blocked Engineering artifact. That restriction belongs only to the older `init --recovery` route. From fresh public checkout recovery facts copy exactly `run_id`, `feature`, `generation`, `candidate_tree_oid`, `authority_digest`; add `paths` in the exact observed order, each with only `path`, `authorization`, `provenance`. Do not copy the legacy `base_tree_oid` or `kind` fields into this packet. Never infer authorization from a commit. It preserves only a proven unaffected prefix; authority changes still reconverge upstream.
- Physical-context handoff: apply [Working-set checkpoint and rotation](stage-handoff-invariant.md#working-set-checkpoint-and-rotation). An accepted next slice normally receives a fresh Engineer under its newly issued logical identity, without an extra rotate. Exceptional replacement of unfinished idle work uses `rotate-owner --id --expected-generation --reason` after a truthful consumed result; for incomplete Engineering use fail with remaining work, not an invented external blocker. Ordinary related repairs retain the owner.
- Runtime update: `pin-runtime --destination <new immutable directory>` verifies and copies only the bundle, not the product checkout. Use its returned launcher/digest for the run. A necessary hotfix follows separately authorized maintenance and appropriate revalidation; do not alter a pinned copy in place.

Successful `recover-capability` restores eligibility and returns the current `next_action`; it does not issue an assignment or dispatch a worker. If that action is `next`, the Director executes its ordinary `step --through-handoff`, then forwards the returned generated `dispatch` to the eligible existing role owner. The new assignment carries the bound recovery evidence so its worker can act on the resolved prerequisite. A continuing owner's eligible baseline may produce a delta. Recovery itself authorizes no reused QA PASS or repeat of unaffected stages.

Other established recovery forms remain in the [protocol](pipeline-protocol.md). If a route rejects its required binding, the Director follows that category's bounded routing row; the authorized responsible specialist investigates any substantive cause. Do not edit state or substitute a broader recovery to bypass refusal. Host capacity/liveness is a Director/host concern, not something these commands repair.

For `recover-capability`, the authorized specialist supplies the exact `prerequisite`, `resolution`, `evidence`, `unchanged_dependencies` values. For `reconcile`, the Director copies fresh native binding and ordered paths and supplies actual per-path authorization; the responsible specialist supplies exact path-origin provenance. The Director may assemble that existing packet once at a retained exact workflow-local path and submits it unchanged. Obtain missing semantic input by one correlated existing-role caller task; do not invent provenance or write product/runtime/state files. Preserve the path/bytes for replay; no new packet schema is introduced.

Retained or reconciled changes do not silently disappear when the new write scope is narrower. The controller supplies bound read-only Review obligations with their source tree/generation and authorization/provenance; these do not grant write rights. Consume them with the exact issued target, preserve the distinction between historical evidence and current product behavior, and close them only after actual current Review and QA. If a product fix needs another write path, use its scoped authority route rather than treating review access as permission to edit.
