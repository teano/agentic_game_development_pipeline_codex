# GameDev Refinement

The primary agent of the current chat owns the batch. It interprets the user's feedback, routes work to real subagents, manages shared files and runtimes, and reports the integrated result. Keep that same primary agent when a full-cycle chat previously delegated Implementation.

## Enter from the right chat

- **Continuing the delivery chat.** When the user gives follow-up work on the feature just delivered, or returns an item from its current batch, use this procedure directly. A new command or approval of a batch of clearly authorized changes is unnecessary. Implementation's unfinished slice repairs stay with Implementation. A question, request to discuss, or request for options authorizes only that activity.
- **Transferring to a different chat.** Require explicit invocation and enough description to identify what is being refined. The user may provide an old chat link, but need not know its ID. Resolve the project and feature; use the existing implementation/refinement note, branch or worktree, feature directory and candidate to locate the original Implementation chat and any later batch handoff. Use the available chat-history tools to open a supplied or recorded locator, or search active and archived chats and read plausible matches. Confirm the feature, tested version, decisions, limits, pending items and worker/reviewer handles against the actual conversation and checkout. A matching title or branch alone is insufficient. If records conflict, the origin is inaccessible, or several candidates still fit, explain what could not be resolved and ask only for the missing distinction or locator before dependent writes. In an unrelated chat ordinary feedback alone does not activate this stage.

Use the [project and handoff procedure](../gamedev-pipeline/references/artifacts-and-approval.md). In Codex, use `list_threads` for discovery when necessary and `read_thread` to read relevant turns. Keep the original chat ID and any delegated owner's handle distinct from the current coordinator. Preserve them when updating the note. Recover the original code and evidence locators, current candidate, applicable project instructions and actual authority. A supplied build can differ from the checkout. Establish which version showed the symptom and which one is being changed. Confirm earlier writes and jobs are quiescent before transferring ownership. The destination chat coordinates its workers directly. When a prior handle is reachable only through its owning chat, use that owner solely to relay the bounded recheck or repair if authorized and supported. Reading history alone does not authorize messaging another user-owned chat. If a required relay needs permission, identify that specific owner and request, keep its check pending, and continue independent work. Verify the actual result and handle.

## Turn the batch into assignments

On a writable transfer, update the existing handoff before dispatch: retain the source chat locator, name the new coordinating chat, identify the quiescent candidate and list the item(s) being taken over or reopened. A read-only context lookup leaves ownership unchanged.

Keep the user's numbering and wording, attachments, requested environment, model overrides, protected behavior and deferred items. In the feature's existing note link each item to its expected result, owner, current evidence and status. When a user returns an item, retain its ID, previous attempt and evidence and record the new observation. New instructions can add, narrow or defer work during a batch.

Distinguish a request to fix, a request to investigate, and a request to show options or a plan first. A clear local change can proceed immediately. For a new product decision or a change to approved behavior, preserve the user's actual decision, update affected obligations through their owning stage and rebind the documents that changed. A larger separate feature can start its own cycle. An ordinary refinement does not reopen the whole PRD, specification and plan.

Choose the operation, model and effort for each item before grouping. Combine items when they share a mechanism and verification method. Keep unrelated diagnoses, visual work and data operations as bounded assignments under the [Implementation routing policy](../gamedev-pipeline/references/agent-model-policy.md). A single checkout, scarce runtime or shared file determines when workers may write or run; it does not give the hardest item's model the entire batch. Sequence ownership at those boundaries. Independent read-only investigations can proceed in parallel. Record the item IDs and actual worker/checker handles for each assignment.

For a fresh unit assign a fresh bounded worker and an independent checker for product changes; one checker may cover related items on the same candidate. Start that checker when there is a candidate or useful independent work to inspect. Delegate reproduction, edits and detailed investigation. The chat owner may read a screenshot, result or diff to scope the item or judge the evidence. Give new pixel measurements, profiling runs and diagnostic probes to the responsible worker; ask for the decisive observation when evidence is missing. The chat owner retains scope, candidate identity, routing, decisions and escalation. Respect a request for fresh agents or a specific model within its stated scope. Only one writer owns overlapping files and only one operator controls a mutable runtime at a time.

## Verify, return and deliver

Give each checker the original symptom and expected result, the delivered candidate and the real environment needed. Request evidence that distinguishes the old behavior from the intended one: a player action, comparable timings, a frame or a built artifact as appropriate. Keep a device-only or live-SDK observation pending if only a local substitute was exercised. A research or preview item can finish with findings or options without a product edit.

On a returned item, send the new observation and previous attempt to its original engineer and checker when reachable. Keep unaffected items and evidence; repeat checks for any shared paths or behavior affected by the repair. If an ordinary worker was lost, reconcile its work and quiescence, then hand off explicitly. For persistent failure follow the [Implementation diagnostic and repair procedure](../gamedev-pipeline/SKILL.md#persist-through-recoverable-failures).

At a stable integrated delivery run affected gameplay and regression checks, and apply the [final architecture review](../gamedev-pipeline/SKILL.md#final-architecture-review) once for that candidate across the batch. Reuse the feature's actual Astra reviewer by handle. On a legacy feature with no prior final architecture assignment, create it once. If an assigned reviewer cannot be recovered, report its review pending. For unchanged product and applicable rules reuse still-valid acceptance. Keep the chat, candidate, item-to-worker links, reviewer handle and open work in the same handoff note so another chat can resume.

Return a short result in the user's numbering: changes or findings, actual verification, unresolved observations and the version/build to check. Distinguish agent verification from the user's manual acceptance. Keep the batch open to further feedback without an idle worker or an automatic new round. Build, release, publication and other external actions retain their original permission boundaries.
