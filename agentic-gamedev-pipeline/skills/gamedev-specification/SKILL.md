# GameDev Specification

## Activation gate

Proceed only on the explicit activation described above. A missing/stale specification, technical question, or implementation request is not authorization. Do not activate another GameDev stage.

Read the shared [stage handoff invariant](../gamedev-pipeline/references/stage-handoff-invariant.md) and [specification-contract.md](references/specification-contract.md). The contract is canonical for artifact paths, trace shapes, worker outputs, holds, and readiness evidence.

Act as Specification Director. Own orchestration, deterministic state, hashes, budgets, handoffs, and user questions. Do not write or proofread the specification in the Director context. Use `scripts/specification_state.py` for every transition; never edit its JSON state directly.

Apply the contract's single **scope and sufficiency invariant** to the Director, Generator, Architect, and Proofreader. The exact approved PRD is the complete product scope. Repository evidence may determine the smallest way to satisfy a named PRD requirement or a proven necessary current integration path, but it never creates another obligation. Require the Generator, Architect, and Proofreader to accept a finding only when it supplies concrete current-project evidence, names the affected PRD ID and material violation, and states the smallest required resolution. They reject theoretical, unlikely, low-probability, or rare risks without evidence that they affect a current supported path, as well as future-scale design, unsupported misuse, optional hardening/cleanup/refactoring, suggestions, backlog, and attempts to find "what else to improve." Apply KISS/YAGNI in both directions: remove unjustified complexity already in the specification and never require new complexity without authority. The Director includes this invariant in every internal worker packet and routes the resulting evidence but does not judge its semantic satisfaction. Stop dispatching work as soon as mandatory coverage, a minimally sufficient design, and the absence of blocking admissible findings are proven. Only the contract's strictly bounded Engineer-resolvable Minor details may remain.

## Establish authority

1. Resolve the project root, lowercase feature, canonical PRD, and canonical specification through the contract. Ask one path question only if ambiguity remains.
2. Require `PRD_READY` on the exact canonical approved PRD. Independently run `../gamedev-requirements/scripts/validate_product_requirements.py <prd> --require-approved` and record its exact-byte SHA-256; `init`, `accept-spec`, schema migration, `revise-in-progress`, and both `revise-ready` routes repeat that complete validator before mutating state or specification bytes. Legacy/malformed authority requires a controlled PRD revision and reapproval; do not activate the Requirements stage or grandfather it.
3. Initialize `.agentic-pipeline/specification-state.json` with `init --prd <resolved-prd> --spec <resolved-spec>`. Treat controller output as phase authority.
4. Assign one persistent Technical Spec Architect before generation. The Generator/helper owns specification writes; the persistent Architect performs pre-accept semantic assessment and remains the sole semantic correction owner after acceptance. Give every internal worker only canonical paths, exact hashes, role contract, current finding IDs, and a bounded task packet—not accumulated chat history.

If an active Proofreader wave in `reviewing` has a completed `record-proofread` result bound to an earlier approved PRD and the PRD has since been freshly approved at a higher revision, use controller `revise-in-progress --reason <exact reason> --architect-id <fresh-id>`. This pre-runtime transition archives the superseded wave and its findings, increments the specification revision, installs the new PRD trace, demotes to draft, and enters `awaiting_accept` with a fresh Architect. Never rerun `init`, edit controller state, carry old findings forward as live blockers, or reuse old review credit. Run `accept-spec`, a fresh Proofreader cycle, and `confirm-ready` against the new authority.

If an exact `SPEC_READY` specification is bound to an earlier approved PRD and the PRD has since been freshly approved at a higher revision with changed exact bytes, use controller `revise-ready --reason <exact reason> --architect-id <fresh-id>` before editing the specification. Schema-10 migration is unsupported by `git-tree-v1`: any legacy state/findings residue fails closed until it is archived and a fresh Plan/`init` is run. A sole valid direct v2 runtime authorizes this tokenless PRD-change route only when its stored authority exactly binds the prior PRD and prior ready specification and a byte-nonmutating public `status` exposes `next_action.kind: command`, `next_action.command: init`, and `next_action.user_input_required: false`. That `init` is the controller-owned archival/reconfiguration boundary after the specification and plan are reconverged, so an old active assignment, open gate, or open question does not block the Specification rewind. Terminal status, checkout recovery, a non-`init` command, user input, an unknown effect, a recovery token, multiple v2 states, or invalid/foreign authority fails closed. The Specification controller creates no runtime hold, retirement record, or token. The transition archives prior PRD/SPEC/Proofreader/Architect readiness provenance, increments the sole specification revision, installs the new PRD trace, demotes to draft, revokes readiness, and enters `awaiting_accept`. After the revised draft bytes are ready, run `accept-spec` to persist a receipt bound to the exact PRD/spec/revision/runtime authorization; `start-cycle` rejects absent or stale receipts. Then run fresh proofreading cycle(s) and `confirm-ready`; old confirmation never carries forward.

When product authority is unchanged and only the exact ready specification needs a sanctioned correction, use the same command with `--specification-only`. This route requires the exact unchanged approved PRD to pass the complete current Requirements validator before reopening and preserves its trace; it never invents a PRD revision or legitimizes a legacy invalid PRD. A sole valid direct v2 state may use this existing tokenless route only when no schema-10 residue exists, the v2 authority exactly binds this project, PRD, and prior ready specification, `active_assignment` is null, and public `status` reports no open gate or question and neither a terminal state nor checkout recovery; closed gates and answered questions may remain only as validated audit history. A recovery token is rejected for v2. The nested authorization uses schema 2 and persists the revision kind, exact prior runtime requirements/specification paths and SHAs, runtime-state path, and exact v2 state SHA. The exact released tokenless schema-1 authorization remains readable only for a canonical `--specification-only` pending transition or latest committed reopen receipt; it is normalized in memory and never rewritten in state or history. Pending completion, committed replay, acceptance, every proofreading transition, and confirmation revalidate that same prior binding and exact runtime bytes; they never substitute the newly approved PRD or coerce a PRD-change rewind into `--specification-only`. After a committed reopen reaches `awaiting_accept`, an exact replay bound to the unchanged final history receipt, PRD, draft, runtime authorization, and lifecycle projection is a byte-noop; changed inputs or any subsequent Architect/lifecycle progress fail closed. The same fresh Architect, acceptance, proofreading, and fresh confirmation invariants apply.

## Generate only when required

If the specification is missing or stale, use exactly one bounded internal Generator; otherwise skip generation. Never run competing generators.

The bounded Generator is an orchestration wrapper around the external `$skill-specification-pipeline`, not a second generator implementation. First run controller `prepare-helper --operation generation`. The controller writes one immutable one-use request bound to the operation, exact PRD path/revision/SHA, canonical specification path, absent marker or exact input SHA, approved language, external helper entrypoint/emitter fingerprints, the exact resolved absolute current `scripts/specification_state.py` path and SHA-256, and exact allowed write paths. Pass that request's absolute path to the actual external skill as `GAMEDEV_HELPER_REQUEST_PATH` and pass the same request-bound controller path as `GAMEDEV_SPECIFICATION_CONTROLLER_PATH`, alongside the skill's normal `TARGET_OPERATION`, `SPECIFICATION_PATH`, and PRD-language `USER_REQUEST` inputs. The helper-derived `USER_LANGUAGE` must equal the approved PRD language. The helper may write only the request-authorized specification, helper report, coverage artifact, and result sidecar paths.

The external helper retains sole ownership of its mandatory stages, passes, mode routing, and global not-applicable policy. The GameDev wrapper MUST NOT skip, duplicate, parse, normalize, or locally reimplement that topology. The scope and sufficiency invariant constrains helper findings and specification content without changing the external workflow's semantics.

After the helper completes with its generic PASS outcome and writes the specification plus opaque report and coverage artifacts, its emitter MUST first prove that `GAMEDEV_SPECIFICATION_CONTROLLER_PATH` exactly matches the request-bound resolved path and SHA-256, then run exact read-only controller command `python -B <GAMEDEV_SPECIFICATION_CONTROLLER_PATH> --project-root <project-root> preflight-helper-output --request <GAMEDEV_HELPER_REQUEST_PATH>`. The canonical controller preflight requires the exact PRD trace, one positive integer specification revision, `status: draft|approved`, and specification language equal to the request-bound approved PRD language. The emitter creates the one helper-owned immutable result sidecar only after validating the exact schema-1 controller/request/output SHA envelope. Then run `record-helper-result`; the controller reuses the same canonical output preflight and validates the exact request/result/output SHA chain, operation/route, language and authority bindings, external helper fingerprints, exact write set, artifact SHAs, and one-use consumption. It never reconstructs or interprets detailed stage/pass status. The Director MUST NOT author the result sidecar, make the semantic acceptance decision, or edit the draft. The same persistent Architect then performs the read-only pre-accept semantic assessment.

That assessment MUST return the contract's non-empty section-applicability/minimality inventory bound to the exact assessed draft SHA. It inventories every authored top-level section and every standalone diagram, table, hierarchy description, and footer block. The Architect MUST reject and enumerate a remove-or-merge correction for an absent-topic section that merely says `none`, `not applicable`, `no data`, or equivalent; a hierarchy or diagram that only repeats another description without distinct PRD-backed behavior; an empty Open Questions, Assumptions, or Risks section or footer; and a generic scalar "data model" table when the PRD requires no data, configuration, or persistence model. A substantively PRD-backed instance remains valid: for example, a data-model section defining a required persisted schema, or a diagram exposing distinct required interaction behavior. Mandatory helper passes still execute under global applicability policy; an executed pass does not make an empty output section mandatory. The Director mechanically rejects a missing, stale-SHA, or blank inventory, but does not decide whether an inventory rationale is semantically true.

On rejection, the Architect returns one exact enumerated correction packet through the Director. Before any write, run `prepare-helper --operation correction --correction-id <id>` for every enumerated ID. Pass its `GAMEDEV_HELPER_REQUEST_PATH` to the same external skill with `TARGET_OPERATION=continue`, the same exact `SPECIFICATION_PATH`, and a PRD-language explicit write/apply request. Route `spec-assistant -> fragment-capture`, then run `record-helper-result` before returning the result to the same Architect. Any input/request/result/SHA drift fails closed and requires reassessment before a replacement request.

The Generator MUST NOT use a local generation fallback or patch around the helper. If the helper is unavailable, cannot honor the bindings/write boundary, derives a mismatched language, or returns invalid output, fail closed with a specification-helper integration error. Generation never grants readiness.

The sole recovery for an already-issued immutable initial-generation `PASS` created before this canonical output preflight existed is `reject-helper-result --request-id <id> --reason <text>`. It is valid only in unchanged `needs_generation` when the controller proves the exact initial request/result/report/coverage/specification fingerprint chain, the output fails the canonical specification authority preflight, and no helper credit or later progress exists. The command preserves every artifact and specification byte, records one rejection receipt, and preserves the invalid draft SHA as the next generation input. Its exact immediate replay is a byte-noop; wrong ID/reason, valid output, drift, or later progress fails closed. Run `prepare-helper --operation generation` next: it issues the next HREQ, includes the current controller path/SHA binding, and routes `continue` from that preserved SHA. Correction remains forbidden until this replacement generation is consumed. This recovery alone may accept the legacy initial request without a controller binding and validate recorded helper fingerprints without requiring them to equal post-fix current helper fingerprints.

For `needs_generation`, `accept-spec` requires a consumed generation request/result chain ending at the exact current specification SHA. Pre-accept and active-wave byte changes likewise require consumed correction results forming an uninterrupted chain from the exact prior SHA. A local draft, Director-authored result JSON, unprepared write, replay, or stale/foreign sidecar fails closed without controller-state mutation.

Only after the persistent Architect accepts the semantic draft and the controller has consumed the exact helper result chain may the Director run `accept-spec --preaccept-receipt <in-project-json>`, end the Generator, and route to `start-cycle`. The controller, not prose, enforces both the helper-result binding and the exact Architect receipt/locator gate. Architect receipt schema is exact JSON object version `schema: 1` with only `schema`, `architect_id`, `prd_sha256`, `assessed_spec_sha256`, `semantic_assessment`, and `section_applicability_inventory`. The identity must equal the controller's persistent Architect, both hashes must equal current immutable PRD/spec bytes, and `semantic_assessment` must be exact `accept`. The controller derives bounded Markdown locators for every `##` top-level section plus standalone fenced diagram/hierarchy/block, a contiguous Markdown list only when indentation proves actual nesting, Markdown table/image, and a final blank-separated unheaded no-content register limited to assumptions, source conflicts, risks, open questions, and additional product obligations. Ordinary flat lists, ordinary prose paragraphs, and a section's sole prose paragraph are not extra structural items. The non-empty inventory must cover that exact locator set once; every exact row contains only non-blank `locator`, exact `disposition: retain`, and non-blank `authority_or_rationale`. Any active helper request, missing result chain, `reject`, `remove`, `merge`, `defer`, missing/extra/duplicate/blank row, malformed/stale receipt, or identity/hash mismatch blocks acceptance without changing controller state. The controller revalidates the same current evidence, PRD/spec authority, and acceptance-before-wave timestamp at `start-cycle`, `record-proofread`, `complete-cycle`, and `confirm-ready`. `accept-spec` is forbidden while a Proofreader wave is active. Any rejected item must be corrected through a fresh controller request and the external helper, consumed, and assessed again against the resulting new SHA before acceptance. No Proofreader credit exists before that acceptance.

## Converge with one writer

The Architect has already completed the pre-accept semantic assessment against the approved PRD, project rules, and only the current repository evidence needed for PRD-required integration paths. After acceptance it remains the sole semantic correction owner, authorizes only enumerated corrections, and may use bounded internal read-only repository workers for exact disputed questions, but every byte-changing correction still routes through the same bounded Generator and `$skill-specification-pipeline`; neither role may activate another GameDev stage, perform broad discovery, or broaden product scope.

For each wave:

1. Run `start-cycle`, then assign exactly one fresh internal Proofreader.
2. Give the Proofreader immutable PRD/spec hashes and the scope and sufficiency invariant. Require a complete but bounded read-only comparison and one deduplicated batch containing only admissible findings. The Proofreader stops early once no blocking admissible finding remains and passes without suggestions or backlog; only the contract's strictly bounded Engineer-resolvable Minor details may accompany that pass.
3. Run `record-proofread`. If every readiness gate passes, have the same Architect confirm the unchanged specification and run `confirm-ready`.
4. Otherwise give one deduplicated technical batch to the same Architect. If no edit is required, run `complete-cycle` unchanged. If bytes must change, prepare the correction request against the exact reviewed SHA, run the same external helper, consume its result with `record-helper-result`, then run `complete-cycle`. The controller validates the old acceptance against the wave input SHA, closes the wave with the consumed helper result SHA, enters `awaiting_accept`, and requires a new exact-SHA Architect pre-accept receipt plus `accept-spec` before another `start-cycle`.
5. Repeat with a fresh Proofreader. A Proofreader never edits; the Architect never awards its own clean credit.

One Architect may complete at most five Proofreader-to-response cycles. An attempted sixth enters `spec_convergence_hold`. Resume only through a recorded handoff to a distinct Architect or a user gate; preserve total waves, prior owners, findings, hashes, and budget history.

The Architect may resolve technical choices supported by project evidence. Escalate product semantics, observable outcomes, scope, ownership, system/public boundaries, or PRD contradictions to one consolidated user decision. Do not disguise them as assumptions.

## Complete the stage

Run `confirm-ready` only on the exact snapshot satisfying every readiness condition in the contract. Return:

- `SPEC_READY: yes|no`, state path, PRD/spec paths and hashes, Architect cycle count, and total waves;
- exact blocking finding/question IDs or the validated readiness evidence;
- `NEXT_ACTION: $gamedev-development-plan` when `SPEC_READY: yes`, otherwise `NEXT_ACTION: user-decision` or `NEXT_ACTION: $gamedev-specification`.

Do not activate the Development Plan stage. Stop after persisting state and returning the handoff.
